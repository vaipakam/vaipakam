# Release Notes — 2026-10-07

Internal matching now leaves a record of what it cleared from a loan. Where that record is complete and readable, the lender's claim states the amount. An incomplete, missing or unreadable record is stated as such, with no figures. The testnets gained a sanctions test list and a script that configures it, together with the in-app banner a flagged wallet sees.

## Thread — the protocol records what internal matching cleared from a loan, and a lender's claim states it (PR #2444)

The record added for #2374 captures what a loan owed when it defaulted, but it could not cover a loan closed by internal matching. Matching reduces the loan's principal before the loan closes, so by the time the closing status is written the debt has already gone. A lender holding such a position was shown its payout with nothing to set it against. The protocol now keeps a separate record for these loans, taken at the match steps themselves.

Matching can clear a loan in several steps while it stays active, because each step moves only the smaller of the loan's principal and the counterparty's collateral. One snapshot at the last step would therefore miss the earlier ones, so each step adds to the record instead. A step adds the debt it discharged, measured the same way as the default record and at the step's own time: the principal it moved, the interest accrued on that principal that will now never be charged, and the late fee on it. Repayments made between steps are not matching and add nothing. Each step also adds what it paid the lender side, which is the moved principal less the matcher's fee. When a step closes the loan from active, the record is stamped and an event announces it. A public read returns it while the loan stands internally matched.

The record is only stated when it is the whole of what matching cleared. If any step ran while the loan was in the full-collateral fallback, that step settled on the fallback's own basis, which the default record already describes. If the lender had already been paid in part before the first recorded step, through a step taken before this change or through a preclose or offset, the sum would also be partial. In both cases the read reports the record as incomplete, with no figures, rather than an amount it cannot substantiate. A loan closed in a single step before this change has no record. NFT rentals never internal-match and get none.

On an internally matched lender claim, the app now states the principal matching cleared from the loan, and, when any had built up, the interest and late fees that are not charged when a loan closes this way. It then says what the matches paid toward that principal and compares only those two. The gap is the matcher's fee, and the app says so in those words. The text is about the loan and the matches, never "you lent", because the holder may have bought the position. An incomplete record, a missing record and an unreadable record each get their own plain statement. An unreadable one is retried, exactly as the default figure is. If the token's details cannot be read, the amounts are left out but whether the principal was paid in full is still said. The indexer files the new event on the loan's activity timeline, where it never stands in for the match itself. The copy is translated in every supported language.

The record has no effect on VPFI recycling. The matcher's fee here is paid in the loan's own asset. It is not the offer-matching share of the loan initiation fee that the recycling plan lists among the conversion classes deferred to the market era. Closes #2427.

## Thread — a testnet sanctions test list, a script that configures it, and a banner that says why a wallet is flagged (PR #2442)

Until now no script set a Diamond's sanctions oracle on any chain; the step was done by hand or not at all, and on Base Sepolia it had not been done. This adds a configure script. It was first written to point mainnets at Chainalysis's on-chain sanctions oracle, but Chainalysis has retired that oracle: its documentation now says it is no longer supported or maintained, was last updated on 18 March 2026, and is not recommended for production screening. The contracts still answer every read, so nothing on-chain shows that the list stopped growing, and an address designated since then passes every check that reads it. The script therefore refuses every mainnet, including the ones where the retired oracle still answers, rather than install a frozen list as if it were live screening. Which supported source a mainnet uses is an open decision, tracked in #2443.

On a test network the script installs a new testnet-only contract, a sanctions test list, as the whole screen. Before this, no wallet we control could be flagged on a live deployment, so the paths that run only for a flagged wallet could not be exercised: the warning, the blocked actions, the close-outs that stay open, and the frozen-proceeds handling. Only the network's admin can flag or clear an address, every change is logged as an event, ownership moves in two steps, and the contract refuses to be created on any chain that is not on an explicit testnet list. The contract can also extend another sanctions list and pass that list's failures through unchanged, but the script deploys it extending none. A second run reuses the recorded test list only while it extends nothing, the network's admin owns it, and no ownership transfer is pending, so its flags are kept. A Diamond that already screens against such a test list keeps it, even when the deployment record does not name it (the record is filled in instead), so a run never silently drops the flags in force. On a Diamond owned by a timelock the script leaves the oracle as it was and prints the call to schedule; it still deploys and records the test list that call names, so the scheduled call never points at an address with nothing behind it. The configured oracle is written into the chain's deployment record as one entry, replaced whole on each run, and only once the Diamond actually uses it. A dry run writes nothing, and the script follows the same local-only rule for skipping the deployment record as every other deploy step.

The app's flagged-wallet banner now says why the wallet is flagged, and so whom to contact. Its last line used to tell every flagged user to contact Chainalysis. It now reads the configured oracle and names one of: this test network's own test list (contact its operator); the test list and the list it extends (removing it from the test list would not clear the other flag); the test list, with the other list unreadable; the sanctions list the deployment screens against (contact that list's provider); or, when no list flags the wallet itself, the sender it declared while recovering tokens (the flag lifts on its own if that sender is delisted). Both the wallet and its declared sender are read every time and judged the same way, so a flag that comes from the sender also names which list flags the sender and whom to contact. A wallet that is listed itself and whose declared sender is flagged too is told both, since clearing either alone would leave it flagged. A failed read of one never hides what is known of the other, and the banner says what it could not check rather than asserting it. It names no provider, because the Diamond accepts any address as its oracle and a provider cannot be inferred from it. The banner's title and first line now say the wallet is flagged rather than listed, since in the last case the wallet itself is not on any list. When the reason cannot be read, it names no contact and asks for a reload. Whether the wallet is flagged and why it is flagged are now one read, taken at one block, by the same check that blocks new positions everywhere in the app, so the banner can never pair a flag with a reason from another moment, and it appears, changes and clears together with the flag. If that block is replaced while the reads run, they are discarded and repeated, so a short chain reorganisation cannot produce an answer no single moment supports. The check is re-read every 30 seconds, flagged or not, so a flag added or cleared shows or removes the banner without a reload. A failed re-read keeps the last answer instead of being read as a delisting. A slow explanation never holds the warning back: after a few seconds the banner shows without naming a contact, and the next refresh tries again. The new lines are translated in every language that already translates the banner. This ships with the test list so that no network can be switched to the test list before the banner can describe it.

Base Sepolia was switched on 2026-10-07 by the owner running this script: the Diamond, which had no sanctions oracle until then, now screens against the admin's test list alone (no other list beneath it), and the deployment record carries its address. The admin, the Diamond and the treasury were checked unflagged afterwards. Still to do: a live drive with a dev wallet flagged and then cleared. The earlier plan to point Base Sepolia at Chainalysis's oracle (#1562) is dropped, since that oracle is retired. #946 still asks for a deploy phase that runs this step and a verify-time check that refuses a mainnet left without an oracle. Closes #2439 once the drive is done; until then, part of #2439.
