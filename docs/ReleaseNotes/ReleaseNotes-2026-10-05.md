# Release Notes — 2026-10-05

Seven changes merged on this day, and one ordering runs through three of them.
The indexer's deploy now applies its database migrations before it publishes
new code, with a schema gate on the Worker for the automatic deploy route the
repository cannot pin (#2409); that was the prerequisite for the two surfaces
that follow, each of which adds indexer columns — a borrow request's committed
collateral range on Offer Book cards (#2413, closing #2382) and the asset and
amount on Activity rows (#2415, closing #2383), both of them follow-ups from
the 2026-10-03 live review. Base Sepolia was refreshed in place to current
main, which puts the illiquid-collateral refinance fix on the live testnet and
proves it against a copy of the deployed chain (#2411). Two are contract
changes: the pair-level loan-to-value preview now values each token in its own
decimals rather than in raw units (#2418) and the borrower's partial
swap-to-repay route moves into its own facet to get back under the per-contract
size limit (#2423). One is tooling the app decodes with: the combined Diamond
ABI now names the Diamond's own "function does not exist" revert, and the
detector that reads it was moved off message text onto the error's structure
(#2417). Each thread below states its own scope and limits.

## Thread — indexer: migrations before code, and a schema gate for the routes that skip them (PR #2409)

The indexer's deploy now applies its database migrations FIRST and publishes the new Worker only if they applied. There is exactly one applier: the indexer, which owns the schema. Its deploy applies pending migrations, confirms in the database that every migration the build carries is recorded, and only then publishes. An apply that ends without applying (a declined prompt, a partial run, a concurrent deploy that got there first) is judged by the database rather than by an exit status. The keeper and agent bind the same database. Their deploys verify the schema read-only, wait a bounded time for the indexer to apply, and refuse to publish onto an older schema. An intermediate revision had all three apply, and three builds from one merge then raced on the same migration. The single-chain deploy script now deploys the indexer before the keeper and agent, and the testnet and mainnet runbooks say to run the indexer phase first on a release that carries a migration. There is no second apply path. The deploy takes no arguments; a dry run has its own command that never touches the database. Because migrations land while the old Workers are still serving, every migration must be additive; the rule is now written into the schema discipline. They used to publish and then migrate, so on every release with a migration, new code ran against the old schema for the length of the gap — and indefinitely if the migration step failed, because nothing rolled the Worker back. #1149 was that window in production: every scan failed on a missing column and the chain's reading position held until someone read the logs. #2214 asked the question and was closed without the change; this makes it.

The indexer also deploys automatically on every merge through Cloudflare Workers Builds, and that route's deploy command is dashboard configuration the repository cannot see or pin. So the Worker now carries a schema gate as well. The build lists every migration it carries (the whole set, so a migration that fills an old numbering gap cannot slip past); until the database records all of them as applied, every scheduled tick and every chain pass declines, with a log line naming the missing migration and the command that applies it. Nothing is scanned, pruned or swept, and the reading position stays put. On the first tick after the migration lands, ingest resumes by itself, with no redeploy and no cursor repair. A new check in the indexer's typecheck fails CI unless that list matches the migrations directory exactly. The keeper and agent have no gate of their own yet (their automatic deploys are tracked in #2410). The gate holds scheduled work only: every HTTP handler, including the write endpoints, still has to tolerate the older schema itself, and the docs say so.

Operator follow-up, recorded in the indexer README: set the Workers Builds deploy command to the package deploy script, with a build token carrying D1 edit rights. Then the automatic deploy migrates first too, and the gate becomes a backstop. Until that is set, a merge that adds a migration pauses scheduled ingest until someone applies it. This is the prerequisite for #2382 and #2383, both of which add indexer columns.

## Thread — Base Sepolia now refinances loans backed by illiquid collateral (PR #2411)

Base Sepolia was refreshed in place on 5 October, paused briefly from 01:01 to 01:05 UTC, to current main. That deploys #2380's fix: a loan backed by illiquid collateral, where both parties to the replacement loan consented to the illiquid terms, now refinances. The replacement loan is admitted exactly as a new illiquid loan would be. Before this, every such refinance reverted at the final risk check, which asked for a loan-to-value ratio and a health factor that the platform never computes for an asset it values at zero. Live loan 22 is the case that found it.

All 102 transactions succeeded, from the pause through the final unpause. Every facet the deployment script installs was replaced with a fresh copy of main. The upgrade facet the Diamond installs at creation, the vault template and the Diamond address did not change. The refresh found no stale routes to remove. The deployed refinance code matches main's build byte for byte. A test on a copy of the live chain now runs the deployed code with no substitution and passes. It opens an illiquid-collateral loan between fresh accounts, posts a refinance request, and has a second lender accept it: the old loan closes as repaid and the replacement opens with both parties' consent recorded. The same test on a copy taken just before the refresh fails with the illiquid risk-math error. The deployment records are updated: the per-chain file, its provenance record and the consolidated copy the apps and workers read.

Reward custody was again not activated: the owner deferred it on 4 October until the VPFI recycling work is ready. Until then Base Sepolia keeps refusing reward claims and remittances that need freshly funded VPFI. Payouts funded only from recycled VPFI are unaffected.

## Thread — the Offer Book states a borrow request's committed collateral range (PR #2413)

A borrow request can commit a collateral range: a floor, and a ceiling up to which a matched fill may lock more. The Offer Book card used to show only the floor, worded "at least X" since #2378 because the market data did not carry the ceiling. The indexer now records both the effective ceiling and the part that earlier matched fills have consumed. Effective means a single-value request is stored with its ceiling equal to its floor, so readers never meet the chain's zero sentinel. Whether a row's range needs reading is recorded explicitly rather than inferred: the migration marks every active offer, every new offer is inserted marked (its creation read is taken at the newest block by design, so it leaves the range to a read pinned to the settled block), and a match marks the borrower offer it consumed part of. The detail-refresh lane re-reads marked rows at the block the scan has settled and clears the mark only when the read completes. It runs on every pass, including the ones that find no new blocks, so a backlog keeps draining. An earlier revision inferred "needs reading" from which columns were empty; review kept finding rows that inference missed, so the mark replaced it. Under borrower-side partial fills a request stays open with part of its range used, which is why the borrower side is tracked at all.

The card now states the request's own terms, and only those: the collateral the request holds now — the whole ceiling for an unfilled request, what is left of it for one that earlier matched fills have part-used — its floor, and that how much a given fill locks depends on how the request is filled. An earlier draft also described what a direct funding and a matched fill each lock; review found, one round after another, a path or a deployment setting that contradicted each such sentence (a matched fill locking less than the floor, a refinance that carries over the old loan's collateral, whether unused collateral is refunded or stays committed depending on whether partial fills are on). Those sentences were removed rather than patched further, since the card reads none of the things that decide them. A part-used request keeps the same terms and also states how much earlier fills consumed (a running total, not what is locked today); a remainder below the request's floor is stated as such rather than shown as available. If the token's details cannot be read, a known range is still stated, in raw base units, with that failure named. A borrow request's loan-to-value names its basis: the requested amount against the request's collateral floor. Until the indexer has read a request's ceiling and the part already used (older rows are re-read by the detail-refresh lane, oldest first), the card keeps the honest "at least X". The loan-to-value line keeps marking every borrow request "a fill of another size can differ", for the same reason: knowing the ceiling narrows the range of outcomes, it does not remove the matched-fill path. For a request earlier fills have part-used, it gives no ratio at all and says why: each further fill sets its own amounts, so there is no single pair to take one at.

The detail-refresh lane reads the chain at the block the scan has settled, not at the newest block, so a match, amendment or transfer the scan has not yet processed — and which could still be reorganised away — is never written ahead of its event. It also keeps an offer's recorded holder when its position-token owner cannot be read, instead of writing the creator back over a transferee; only a row with no recorded holder falls back to the creator.

Re-reading every older active offer is a large backlog for the first ticks after the migration. The refresh lanes now run last in each scan, after it has recorded its progress and finished every once-per-scan step, so however much they spend they can only delay heal work, never stall the scan; they also stop starting rows once the invocation's request or database-query allowance is nearly used, and pick up the rest on later ticks.

The new columns arrive by a database migration, which the deploy now applies before publishing (#2409). Until it lands, the Worker's schema gate holds scheduled writes, and the offer API keeps answering because it reads whatever columns exist. Closes #2382.

## Thread — Activity rows state what they moved or offered (PR #2415)

Activity rows showed an event label, a loan or offer number and a time, but not the asset or amount the transaction moved or offered, which the 2026-10-03 live review asked for. An earlier attempt (#2378) rebuilt the amount in the app from each row's raw event data, and three review rounds kept finding new edges of that one approach: offer terms nested inside a terms structure, a loan's amount and asset split across two events, several offers or loans in one batched transaction, claims that do not say whether they moved a token or an NFT, and a range offer whose first figure is only its minimum. All of that is knowledge the history service already has while it reads the chain, so this change fixes the value there, once.

Each activity row now carries a normalized asset, asset type, amount (with a ceiling for a range) and NFT token id, established at ingest from the event itself, its companion events in the same transaction (matched by offer or loan id, so a batched transaction gives every row its own value), and the loan and offer records. Claims take their asset type from the loan: the principal side, the collateral side, or an NFT rental's fee asset; a claim the loan cannot place unambiguously gets no type and no amount. An NFT never gets an amount. Events with no single amount, such as repayments, carry none. The companion events stay off the loan and offer timelines as before; the value reaches the main row without adding a second entry.

The app shows the value on the row: an exact amount, "X–Y" for a range, or the NFT by its token, with an ERC-1155's number of copies. A token amount names its contract beside its symbol, since two tokens can report the same symbol. A row states every value its action moved for its own loan or offer — a borrower claim paying collateral and a frozen surplus in different assets shows both — and says so when the same action moved something not itemised, such as a borrower's fee rebate. A lender claim notes that it also pays out any funds held for the lender from earlier top-ups, which its amount does not include. Collateral top-ups now state the amount added. While a token's details load the row says the amount is loading, and if they cannot be read it states the figure as base units of that contract; a row whose value the history service could not establish says the amount was not recorded. The new columns arrive by an additive database migration that the deploy applies before publishing; rows recorded before it carry no value and say so, and the activity API keeps answering on the older schema. Closes #2383.

## Thread — The combined Diamond ABI names the Diamond's own "function does not exist" revert (PR #2417)

The combined Diamond ABI that the app and the Workers decode with was built from the facets alone. One revert is raised by the Diamond contract itself rather than by any facet: when a call names a function no facet hosts, the Diamond answers "function does not exist". That is exactly the revert a stale ABI or a partially refreshed deployment produces, and it was the one error nothing could name. The Diamond contract now ships its own ABI alongside the facets', and the combined ABI takes its errors and events (never its constructor or its catch-all entry points). A deploy-sanity test pins that entry to the compiled contract, and the package test fails if any error the Diamond declares drops out of the combined ABI.

Decoding that revert changed what its message says: it now reads by name rather than as a raw four-byte code, and the app's "older deployment without this view" detector looked for the raw code in the message text. Left alone, every check that deliberately lets an older deployment through would have started failing instead. The detector now reads the revert data from the error's structure, which is the same whether or not the name was decoded, and keeps the text match only as a fallback for errors that do not come from viem. The same blind spot in the shared client library's copy of the detector is closed. Behaviour users see is unchanged by design; this is covered by new tests that drive a real viem client against the new ABI.

Closes #2399.

## Thread — The pair-level loan-to-value preview values each token in its own units (PR #2418)

The oracle facet exposes a read-only preview of the loan-to-value of a given borrowed amount against a given collateral amount. It divided each leg by its price feed's decimals but never by the token's own decimals, so both legs entered the ratio in raw token units. For two tokens with the same number of decimals that cancelled out; for a pair with different decimals, such as a 6-decimal stablecoin against an 18-decimal asset, the result was off by a factor of ten to the power of the difference. It also answered a zero collateral amount with a loan-to-value of 0, which reads as "no risk", where the loan-level calculation refuses.

No protocol path used the preview, but it is a public surface an integrator, a keeper or the app could reasonably trust; the Offer Book work in #2384 was about to. It now values each leg in the same terms as loan initiation, liquidation, adding collateral and refinancing: price over the feed's decimals and over the token's own decimals. It takes the ratio in one step instead of from two separately rounded values, so the answer is the exact loan-to-value rounded down only to whole basis points: a small borrow is never rounded away to a value of zero and reported as "no risk", however small either side is. A collateral leg that values to nothing is refused with the same zero-collateral error the loan-level calculation uses. The loan-level calculation itself still rounds each leg down to whole units; that is a separate, binding-path question, tracked in #2419. A risk-math comment that pointed at the old formula is corrected. Closes #2403.

## Thread — The partial swap-to-repay route gets its own facet (PR #2423)

The swap-to-repay facet hosted both of the borrower's swap routes — paying a loan off in full by swapping collateral into the principal asset, and paying part of it down the same way — and had grown to within 73 bytes of the per-contract size limit every chain enforces. That is less than any guard costs, so no further change to either route could be deployed: the refinance-request guard planned for the partial route in #2407 would have pushed the facet over the limit.

The partial route now lives in its own facet. This is a pure move: the function keeps the same name, the same address (the protocol's single entry point) and the same behaviour, and reads and writes the same storage, so nothing changes for a borrower, the app, a keeper or an indexer. Only the deployed bytecode is split across two contracts. Operators should note that the two facets are one surface and must always be refreshed together; the all-facets refresh script carries both. The full-repayment facet now has roughly 4 KB of headroom and the new partial facet roughly 9 KB. Closes #2416.
