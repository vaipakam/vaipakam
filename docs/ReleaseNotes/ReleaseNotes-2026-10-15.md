# Release Notes — 2026-10-15

The keeper's move to an always-on machine continued: it now has an install kit that redeploys it on every merge, and a lease so that only one copy runs at a time, wherever it is hosted. It now sends a health-factor liquidation that an internal match can close even when no swap venue quotes. It also no longer reports illiquid loans or zero-collateral rentals as failed health-factor reads. The indexer shows internally matched loans as settled once both sides have claimed, and the ingest-health alert can no longer hang on a GitHub call or fail without saying so.

## Indexer — internally matched loans now show as settled once claimed (#2464)

When both sides of an internally matched loan have claimed, the protocol settles it. The indexer kept showing these loans as internally matched anyway, so the loan page, Positions and the desk read as if claims were still pending. The handler for the protocol's settlement event only accepted a hand-written list of earlier states (repaid, defaulted, liquidated) and left internally matched loans out. Meanwhile the handler for general status changes deliberately leaves this step to the settlement event, so nothing ever corrected the row. On Base Sepolia, loans 24–27 were stuck this way.

The indexer now treats the protocol's settlement event as authoritative: it settles a loan whatever state the loan was in. It no longer keeps a second copy of the contract's rules about where settlement can come from. Loans already stuck this way are settled by a check that runs on every indexer pass, not by a one-time migration. A one-time migration would also miss a settlement that the previous indexer version logs during a deploy without updating the loan. The check only finishes the step that was missed: a loan already shown as repaid, defaulted, liquidated or internally matched, whose settlement the indexer's own event log holds. Before changing anything it confirms with the protocol that the loan really is settled, and it takes the settlement's block only from a logged event whose transaction the chain still confirms in that block, so an event from a block the chain later discarded can supply neither the status nor the date. If no logged event can be confirmed, for example because the node no longer keeps old receipts, the loan is still settled, since the protocol confirmed it, with its block and time recorded as unknown. A later confirmed event fills them in. It only acts on a block the chain has called settled. Settlements recorded by the previous indexer version carry the time the indexer noticed them, not when they happened. Each settlement now records whether its time was read from the chain. A time that was not is shown as unknown rather than as the settlement time. That includes any settlement the previous version records while a deploy is in progress. Already-settled loans are not revisited to re-date them: a settlement whose time could not be verified stays unknown, unless the indexer later replays the same settlement event from a block whose time it can read. When the check settles a loan itself, it dates the settlement by reading the event's block from the chain again, because the time stored in the log can be the indexer's own clock when the original read failed; if that read fails, the time is recorded as unknown rather than guessed. The check works through loans in rotation, so loans it cannot confirm cannot hold up the others. It announces each settlement to connected browsers straight away.

A loan still shown as active but with a settlement in the log has missed its whole closing step. That stays the job of the indexer's existing correction pass, which re-reads the full loan.

When the time of a settlement cannot be read during a scan, the loan is settled with its time recorded as unknown, and a later replay of the same block fills it in. The "we found this by checking" notice from the indexer's correction pass is now tied to an explicit marker that only the correction pass sets (a new additive database column), rather than to what the loan's record happens to look like, so it can no longer be attached to a settlement an event or the settle check wrote. A settlement event for a loan the indexer still shows as active is left to the correction pass, which re-reads the whole loan and clears its listings, rather than changing only its status, and the general status-change handler no longer promotes such a loan to settled behind it in the same scan, which would have hidden it from the correction pass.

Closes #2464.

## Thread — The keeper's always-on machine gets an install kit and deploys itself (PR #2507)

The keeper can already run as one long-running process off Cloudflare. This change adds what it takes to put it on a real machine and keep it current there. One install script, run once on an Ubuntu machine, installs Node 22 from nodejs.org (checked against its published checksum), clones the repository, and sets up two systemd services. The keeper service runs the keeper as a locked-down, short-lived user that receives its settings file as a private credential. An update timer checks the main branch every five minutes and moves the keeper onto each new build. The install never starts the keeper: that is a separate step in the runbook, taken once its settings are in place.

A merge to main is now the keeper's deploy on the machine, as it is for the Workers. The updater builds the keeper as one self-contained file and runs it once to prove it loads. It compares that file with the one already running, so a merge that does not change the keeper does not restart it. Each build is made from an export of exactly the commit being deployed, inside a throwaway sandbox account that exists only for that build. The sandbox can neither read the keeper's settings or signing key nor write the releases the keeper runs, so code being built cannot change what is already deployed. The updater also installs that same commit's service definitions and its own newer version, so the keeper never runs under the settings of another commit. It installs the finished file under a folder named for that commit, then switches the keeper to it, and the keeper restarts after its current tick finishes. Rolling back is pointing the keeper at an earlier release and pausing the timer. If a build fails, the running keeper is left as it was and the next check retries. Nothing stops the keeper by force on a timer, because a forced stop could cut a transaction off between sending and recording. The keeper also starts with an empty environment, so its settings file is the only place a setting can come from.

The settings file now has a committed template. It ships disarmed with every secret blank, and a test keeps it in step with the settings the keeper reads, so a setting cannot be left out by accident. An empty line in that file now means "unset", as an unbound setting does on the Worker. Before this, an empty numeric setting could have been read as zero instead of falling back to its default. The new runbook covers starting the keeper disarmed, what a good tick looks like, and arming.

## Thread — The keeper sends the internal-match liquidation when no venue quotes (PR #2509)

The contract's health-factor liquidation checks for an opposing position it can match the loan against at oracle price before it uses any swap route. The keeper's liquidation stopped as soon as no venue quoted the collateral, so a loan that an internal match could have closed was never sent at all. The in-kind close added in #2487 deliberately refuses an ending that is a match and leaves it to the liquidation, which made the gap visible.

Now, when no venue quotes, the keeper first previews the liquidation with an empty swap list and sends it only when the chain shows that the call settles this loan through an internal match. Any other preview result, including one the network cannot run, sends nothing, and the keeper moves on to the in-kind check as before. The send waits while an earlier keeper transaction is still unconfirmed and goes through the same one-at-a-time submission path as the keeper's other sends. A send whose answer is lost is reported as unknown, with its transaction hash. That send logic is now one shared piece used by both the close-out and this liquidation.

Internal matching is off by governance default, so nothing changes until it is turned on. The behaviour belongs to the liquidation duty and is armed by the keeper-wide switch, which is off on the live deployment. Closes #2501.

## Thread — Only one keeper runs at a time, wherever it is hosted (PR #2508)

The keeper can run on Cloudflare or on an always-on machine, and every copy signs with the same key. Until now, keeping a second copy from running at the same time was a matter of procedure alone. Now every tick first claims a single lease in the shared database under the copy's own name. While another copy holds the lease, the tick does nothing and logs which copy holds it and until when. A copy with no name, or one that cannot reach the database to claim the lease, does nothing either, because it cannot tell that it is the only one running.

A running copy renews the lease every minute, including minutes it skips because its previous tick is still running. A lease that stops being renewed lapses after ten minutes, so a machine that dies hands over to the next copy by itself. The Cloudflare copy is named "cloudflare-worker", and a machine is named after its host name unless its settings name it otherwise. Whether a lease has lapsed is judged by the database's clock, never a copy's own, so a machine whose clock is wrong cannot take a lease that is still live. The lease is a guard, not a fencing token, so the runbook's one-copy procedure still applies: the Worker's schedule stays empty while a machine runs, and an old machine is stopped before a new one starts.

The lease lives in the shared database for now, because that is the only one the machine runner can reach. It is keeper-only state, so it moves to the keeper's own database with the other keeper tables when that database lands.

## Thread — The ingest-health alert can no longer hang or close nothing silently (PR #2510)

The scheduled ingest probe opens and closes a GitHub issue to alert the operator, and posts to the ops Telegram chat as a fallback. Two gaps are closed. First, each GitHub call now has its own short deadline, and each step has one, so a GitHub API that accepts the connection and never answers fails that step quickly instead of running the job into its five-minute limit, where the job would be cancelled before the Telegram fallback could send. Second, a failed lookup of the open alert issues used to look like "none open" and leave the run green with a recovered alert still open; it now fails the step, so the run shows it. Closes #2506.

## Thread — Keeper: a health factor that cannot exist is not an error (PR #2514)

The keeper's health-factor watcher now tells the protocol's own states apart from real failures, using the same rule as the liquidator. An illiquid loan has no health factor by design, because it has no oracle. The watcher used to log that as an error on every tick, and now skips it quietly, as the liquidator already did. A loan whose asset has no price feed cannot have its health factor computed right now. The watcher now names that as a warning ("an asset this loan needs has no price feed"), not as an undecoded revert, because the subscriber's band alerts for that loan cannot be evaluated. Every other failure is still logged as an error. Found on the first disarmed tick of the keeper on its always-on machine, where both states logged as errors and made a clean tick impossible to certify.

## Thread — Keeper: a zero-collateral rental has no health factor by design (PR #2518)

An NFT rental secured by its prepay holds no collateral, and the protocol refuses to compute a health factor for a loan with none. The keeper's liquidator counted those rentals as loans it had failed to evaluate, so on Base Sepolia and BNB Testnet every scan reported itself incomplete because of loan 4, a rental on each chain. Both health-factor passes now treat a zero-collateral rental like an illiquid loan, with no health factor by design. The scan's "incomplete" marker now means a real gap, such as a loan whose asset has no price feed. Found on the keeper's first armed ticks on its always-on machine.
