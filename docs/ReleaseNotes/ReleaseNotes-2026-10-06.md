# Release Notes — 2026-10-06

Four changes with release notes merged on this day, and three of them are one
thread: the refinance request. The protocol now keeps a record of each loan's
request, allows one standing request per loan, and holds the loan still while
that request stands, so a partial repayment, early close, handover, offset or
collateral withdrawal can no longer leave a request unfillable between the
app's last read and the transaction being mined (#2424, closing #2407). The
connected app then reads that record instead of searching the borrower's
offers, and shows any request the record does not name as one that can never
be accepted (#2429, closing #2425). A live drive refinanced a real
illiquid-collateral loan end to end through the deployed app, and while it ran
the production indexer, held by its schema gate, was restored by applying its
two pending column-only migrations (#2434). The fourth is a contract change on
the default side: the protocol now records what a loan owed when it defaulted,
and a lender's claim compares its recovery against that figure (#2426, closing
#2374). A comment-only correction to how the claim code describes the fallback
lender entitlement also merged (#2430); it changes no behaviour and carries no
section.

## Thread — the protocol records what a loan owed when it defaulted, and a lender's claim shows the shortfall against it (PR #2426)

Until now, nothing on chain kept what a loan owed at the moment it defaulted, so the connected app could only say that a lender's default recovery could not be compared with anything. The loan's current principal was not an honest substitute: partial repayments change it, and a holder who bought the lender position on the secondary market never lent it at all. The protocol now records that figure itself. When an ERC-20 loan is liquidated, defaults on time, or enters the full-collateral fallback because its collateral could not be sold, the protocol stores, at that block and in the loan's principal asset, the principal outstanding, the interest outstanding net of anything already settled, and the late fee. This is the basis a liquidation or time-based default settles its debt on. A fallback divides the collateral on its own basis (principal plus interest plus a lender bonus and a treasury share, no late fee), so for a fallback the record states the debt rather than that division. It also notes whether the default went through the fallback. The figure is computed once, at the single place every default status is written, so the forced-close paths themselves are unchanged. That matters because several of them have almost no contract-size room left. A public read returns the record, and an event announces it.

Entering the fallback is treated as the default. When the fallback loan later moves to defaulted at the lender's claim, the figure from the entry is kept rather than restated at the claim's time, because interest kept running in between. The public read reports the record only while the loan still stands defaulted. A fallback that the borrower cures by adding collateral or repays in full, one fully closed by an internal match, and a loan that has since settled all read as having no record. Nothing has to clear it, and a new default overwrites it. The event keeps the history. NFT rentals get no record, because their "principal" is a daily fee and the lender's claim is the NFT itself. Neither do loans fully closed by internal matching straight from active, nor loans that defaulted before this change.

On a defaulted lender claim, the app now states what the loan still owed when it defaulted, with principal and charges shown separately. This is phrased for whoever holds the position now, never as "you lent". It compares the recovery only against the principal, because the protocol takes no share of principal. A recovery below the principal is shown as a shortfall of that amount. Above it, the app says the principal is covered in full and does not count the remaining interest and late fees as a loss, since those are paid after the protocol takes its share. When the recovery may have come in more than one part — proceeds held beside the claim, a claim in another asset, or a default that went through the fallback — the figure is stated without a comparison. A claim on a loan still in the fallback states the recorded figure beside its existing note that the claim can still change the payout, again without a comparison. If the token's details cannot be read, the amounts are not written, but whether the recovery covers the principal is still said, since both are in the same token's units. When there is no record, the earlier "not available" line stays. When the record cannot be read, the app says that instead, and does not reuse that answer from its claim cache, so the claims list retries on its next refresh and the loan page re-reads it within half a minute. The indexer files the new event on the loan's own activity timeline, where it appears translated under the default and never stands in for it; it carries no amount there because it moves no funds. The copy is translated in every supported language. Closes #2374.

## Thread — A real illiquid-collateral loan refinanced through the live app; indexer ingest restored (PR #2434)

Loan 22 on Base Sepolia was refinanced end to end through app.vaipakam.com on 5 October, using the dev test wallets. That loan is backed by illiquid collateral that both parties consented to, and it is the loan whose refinance used to fail (#2380). The borrower posted the refinance request from the loan's page (request #45, 12% for 30 days). A different lender funded it through the app's own review-and-sign steps. All five transactions succeeded, and each wallet's transaction count rose by exactly the transactions the drive saw.

What the committed drive verifies. Its claims were narrowed after review (#2431) to what the transactions' own records and chain reads taken at the accept's block prove directly. There are four. First, the app names the request the borrower's transaction actually created: the "request is live" message must carry that transaction's request number. Second, the old loan is closed as repaid. Third, the accept opened exactly one replacement loan, which is active, belongs to the same borrower and is lent by the lender who accepted. Fourth, the collateral moved with the loan: the old loan's hold on it is released, the new loan holds the same collateral in the same amount, still locked in the borrower's own vault, and the accept moved none of it out of the borrower's vault. The drive also confirms that every signature and transaction was one it expected, and that nothing reached the chain that it had not allowed. The request-number check was added in review after the run, so it is not claimed for loan 22. On loan 22 the other three hold: loan 22 is repaid, loan 23 is active for the same borrower and lender, and loan 23 holds the same 100 units of collateral that loan 22 released.

What this drive does not verify, and says so in its report. It does not check the exact amounts the refinance settled: what the old lender can claim, how each wallet and vault changed, the individual token transfers, or the fee rates recorded on the new loan. Those are covered by the contract test suites, including a test that replays this refinance against a copy of the live chain. It also does not re-check the new loan's other terms beyond these claims. The requests the wallets signed are still compared field by field before signing, but what the protocol stored from them is not re-asserted. The figures on the review screens are checked before consent, as a reason to stop, not as a result. Out of scope as well: a refinance inside the grace window, a loan with liquid collateral, the old lender claiming the payout, how the indexer and the app's lists show the request and the new loan afterwards, reward accounting, and any payoff approval left standing. The app approves the payoff for the request's last fillable moment, so an earlier accept leaves the difference approved; this run left about 0.0000764 WETH. The drive reads state at the end of the accept's block, so a later transaction in that same block could in principle change what it reads. That is stated in the report too.

How the drive reports a problem. Before it writes anything, a failed check is a failure and a missing precondition stops the run without writing. Once it has written something, any stop is reported as undetermined. It lists what the run may have left standing and the state of any replacement loan, and it never claims success. It reports a failure after a write only when the chain contradicts one of these claims: the app naming a different request from the one the transaction created, the old loan still active after the accept went through, no single replacement loan, or the collateral not carried over. It also fails when more transactions reached the chain than it allowed. If the page fails after the accept went through, the drive still checks the accept's claims from the chain.

The drive is committed as a reusable live check, and a rerun against loan 22 now stops before sending anything because the loan is closed.

The drive turned up two things, each filed. First, the lender's review never says the request is a refinance: it does not mention that accepting also pays off and closes the borrower's existing loan, and it describes the carried-over collateral as newly locked (#2421). Second, the production indexer had stopped advancing at 05:35 UTC. The merge that added the offer collateral-range columns was published automatically without its database migration being applied, and the safety check added the same day correctly held all indexing until the schema caught up. The two pending migrations, both of which only add columns, were applied by hand at 09:02 UTC, and indexing resumed on its next scan with no redeploy; it was advancing again by 09:06. Until then, today's new offers and loans were missing from the app's lists. Making the automatic deploy apply migrations first, and alerting when indexing pauses, is tracked in #2420.

## Thread — the protocol holds a loan still under a standing refinance request (PR #2424)

A refinance request is priced against the loan as it stands. Its amount has to cover the outstanding principal, and a carry-over request has to match the loan's collateral exactly. A partial repayment, an early close, an obligation handover, an offset or a collateral withdrawal made while the request stands leaves it impossible for any lender to fill. The connected app already checks for a request just before the wallet opens, but no check made before signing can close the gap between that read and the transaction being mined. The protocol now closes it. While a refinance request stands against a loan, those five actions are refused, and so are partial repayment by swapping collateral and an in-place extension of the loan, which rewrites the rate and term the request was priced against. Each refusal names the loan and the request. The borrower cancels the request first. Full repayment is deliberately not held, because it settles the loan and ends the request with it. Neither is any enforcement action — default, liquidation in full or in part, or the periodic-interest auto-liquidation — because a borrower's own request must never be able to shield a loan from enforcement. A partial liquidation can leave the request unfillable, and that is accepted. Adding collateral is not held either: it is a safety action that has to stay available under price pressure, even though it makes a carry-over request unfillable.

The protocol now keeps a record of each loan's refinance request and allows one standing request per loan. Posting a second request while one stands is refused, so two devices can no longer both post one and leave each other's request unfillable. A request holds the loan while it stands:

- it exists and has not been taken or cancelled;
- it still targets the loan;
- it has not expired;
- the loan is still active;
- its creator still holds the borrower position.

Whether a lender could fill it at this moment is deliberately not part of that rule. The borrower's refinance limits, the funds and approval for paying off the old lender, an overdue interest period, a collateral top-up and the market can each make an acceptance fail, and each of them can change back. Review rounds kept finding one more of these to follow, and each addition still lagged what an acceptance actually checks, so the rule was cut back to the bounded one above. A standing request that can no longer fill keeps holding the loan until the borrower cancels it, and cancelling is always open to them. A separate public check reports, for display, whether the recorded request could be accepted right now and the reason if not: its own state, the borrower's limits, an open offset, a committed swap-to-repay order, overdue interest, and whether a carry-over request still matches the collateral. It cannot report the payoff funds or the market, so a request can pass it and still be refused. A request can never be taken while an offset is open on the loan, because each would close the loan underneath the other.

Standing is worked out when it is read, not stored, so a request that stops standing for any of these reasons stops holding the loan back without any further transaction. A new public read reports the request recorded for a loan and whether it still stands. A lapsed request stays reported, so an expired request that was never cancelled can still be found and cleaned up.

The connected app now explains each of the new refusals in plain words, in every supported language, including when a wallet returns only the raw revert.

The record is authoritative. A lender can take only the request the protocol has recorded for the loan, so the request the guard watches is always the only one that can fill. Without this, a request could drop out of the record — its creator handing the position on and getting it back later — and then become fillable again with nothing guarding the loan underneath it. A new request also never silently drops an old one: while the holder's own earlier request has been neither taken nor cancelled, even after it expires, a new one is refused until the holder cancels it. An expired request can still hold a fresh collateral pledge, and the record is how it is found from the loan. A request posted by a former holder may be replaced, because the new holder could not cancel it and its creator still finds it among their own offers.

A request is also refused while the borrower has an offset open on the loan, because completing the offset closes the loan underneath it. An offset was already refused while a request stands, so neither order can leave a request stranded.

Requests posted before this upgrade are not in the record, and nothing adds them. They can no longer be taken and they do not hold the loan back; a borrower who still wants one cancels it and posts it again. A permissionless migration that recorded them was built and withdrawn during review: every rule it needed to decide which pre-upgrade request to trust (the first of two, one beside an open offset, one whose creator had handed the position on, one already replaced) opened another way for a request to be resurrected or raced. Nothing is live on a mainnet yet, so the cost is a re-post of a testnet request. A refinance a lender already accepted under the earlier step-by-step flow, with its replacement loan created and only the closing of the original pending, always completes, record or not, because refusing it then would leave the borrower owing both loans. The record is checked when a request is taken, not when an already-taken one is closed out.

The record spans several facets — where requests are created, the borrower actions it guards, the refinance itself and the previews — so it must be installed with every facet at once. The two curated partial-refresh scripts now refuse a Diamond that does not have it yet and name the full in-place refresh as the way to roll it out. The acceptance and match previews now report a request that is not the loan's recorded one as unable to complete, instead of advertising an outcome the protocol would refuse. The app still finds a request by its bounded on-chain search; switching it to the new record is a follow-up. Closes #2407.

## Thread — the app finds a loan's refinance request from the protocol's own record (PR #2429)

Since #2407, the protocol keeps a record of each loan's refinance request. It holds the loan back only for that recorded request, and only that request can be accepted. The connected app was still finding requests the old way: a bounded search over the borrower's own offers. That search had two limits. It could fail to answer, and it could stop short for a holder with more offers than one search reads. In both cases the app held back partial repayment, early close, handover, offset and taking collateral back, and said it could not tell.

The app now reads the record first. A request that still stands is the one that holds the loan back, with no search needed. If the recorded request has expired but the current holder never cancelled it, the app shows it as expired so it can be cleaned up, and the refinance form waits for that cancel, as the protocol requires.

The old search now runs only to find leftovers. These are requests the record does not name: one posted before the record existed, or one a newer request replaced. The protocol will never accept a leftover, and it holds nothing back. So when the app finds one, the request card says plainly that it can never be accepted and offers to cancel it. A leftover never stops any action. Cancelling a leftover never removes its payoff approval, because the same approval serves every refinance request the wallet posts on that token and another could be posted from another device at any moment; the card says so and names where to remove it by hand. If the record shows no request standing but its lapsed request's details cannot be read, nothing is held back and only a new post is reported as unconfirmed. A request this device has just posted is shown ahead of any leftover straight away. If the leftover search cannot answer, nothing is held back either, because nothing the protocol would refuse depends on it, but the page says it could not check for an older request and names the manual cleanup.

On a deployment that predates the record, the app keeps using the search alone, as before. If the record itself cannot be read, the affected actions hold back and say so. The new card text is translated in every supported language. Closes #2425.
