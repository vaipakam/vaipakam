## Thread — the mainnet sanctions list: Vaipakam's own OFAC record, plus RedStone where deployed (PR #<n>)

The owner decided the mainnet sanctions source on 2026-10-17 (#2443): Vaipakam keeps its own on-chain list of the digital-currency addresses on OFAC's SDN list, and combines it with RedStone's Sanctions Oracle on chains where RedStone has deployed one. A wallet is flagged if either flags it. Chainalysis's on-chain oracle, which this replaces, was retired in March 2026 and is not configured anywhere. This change adds the list contract and the offline tooling that computes its updates. It does not deploy anything or configure any chain.

The new list contract is meant to be the oracle a mainnet Diamond screens against. Its owner is the chain's admin, with two-step transfer and renouncing disabled. The owner appoints updaters and does not update the list itself unless it appoints itself. Each update records the SHA-256 of the exact OFAC file it was built from, that file's publication date, and the time it was applied, so anyone can read on-chain how current the list is and what it was built from. An update that changes nothing is still recorded. Every address added or removed emits its own event, and the current list can be read in pages from the contract. An update names the list version it was computed against and is refused against any other, all or nothing. Adding a listed address, removing an unlisted one, or adding and removing the same address in one update is refused, so a stale or doubled update fails loudly. Publications only move forward. The publication date is stored in a form that can be ordered, and an update from an older publication is refused, because it would re-list delisted addresses and drop newer designations while still fitting the current list. The same publication is accepted again only as a refresh that changes nothing, and a different file with the recorded date is refused. A deliberate rollback or a same-day OFAC reissue needs a one-time authorization from the owner naming that exact file. The owner cannot authorize a date newer than the recorded one, since a newer publication needs no permission. Any successful update withdraws an authorization that is still outstanding and logs that it did, so an unused permission cannot be spent later. Both the authorization and its use are logged. RedStone's oracle, where used, is fixed at deployment and given as an explicit input. No address is built in, because the only deployment we know of (Ethereum mainnet) has not been verified by us. The contract reports RedStone's own freshness when RedStone provides it, and reports "unknown" when it does not. It can say which of the two sources flags an address. When RedStone cannot be read, an address the own list flags is still flagged, and for any other address the failure goes to the Diamond unchanged. That keeps the Diamond's existing fail-open and fail-closed screens exactly where they were. Answering from the own list alone would quietly turn the fail-closed ones fail-open during a RedStone outage.

The testnet sanctions test list from #2439 now shares its combining rule and its failure behaviour with the mainnet list, through one common base. Its addresses, functions, events and errors are unchanged, and the overlay's existing tests pass unchanged. A new offline tool reads OFAC's SDN Advanced XML (a local copy, or downloaded) and extracts every EVM-format address under any digital-currency label. It drops entries OFAC marks as false and reports malformed values for a person to check. It reads the current list from the contract at one block, fixed by that block's hash (the finalized block unless one is named) so every read describes the same state and a reorganised block is refused, or from a file, and prints what to add and remove, the file's fingerprint and date, and the ready update call. It refuses an incomplete file: the whole input is checked for complete XML structure before anything is extracted, so a truncated download fails wherever it was cut. One reader both checks that structure and extracts the data, so a feature inside a comment or inside a CDATA section is never read as a listing, and escaped characters are decoded exactly or the file is refused. It refuses a file it cannot find addresses in, and a publication older than the one the list records. It refuses a diff removing more than ten addresses unless that bound is deliberately raised. Every numeric option must be a plain non-negative whole number, so a typo cannot switch off a guard. Every value that starts with 0x but is not exactly an address is reported as written, for a person to check. It can also compare once against the retired Chainalysis oracle's logged history, or an exported copy of it, and print three sets: in both, OFAC only, and Chainalysis only. The Chainalysis-only addresses are for review and are never added, because that list stopped recording delistings when it froze. The configure script still refuses every mainnet, now saying why: who runs and signs the list's updater is still an open owner question. Showing the list's freshness in the flagged-wallet banner, and naming OFAC or RedStone there, is a follow-up. Today the banner names "the list the deployment screens against". Refs #2443.
