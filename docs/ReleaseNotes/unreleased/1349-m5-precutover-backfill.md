## Thread — the days that predate the announcement (#1349 M5)

When the daily recycling account started announcing its full composition, the announcement's shape changed. Days finalised before that upgrade were announced under the older shape and simply cannot supply two of the figures — how much fresh issuance was actually drawn, and whether the platform had committed to the day at all. The consumer refuses those days rather than reading the absent figures as zero, which would invent finalised, uncommitted, zero-emission days that look exactly like real ones.

This adds where those days come from instead: a pass that asks the contracts to recompute each one, and a place to keep the answers.

**Keeping them apart from the announced days is the whole design, not tidiness.** Every other record in this area is a fold of the announcement stream, so rebuilding the platform's off-chain state from scratch reproduces it exactly. These are different: the recomputation reads a value that a role handover can legitimately overwrite for a day already closed. Once that happens, asking again returns a different answer and the original is gone — those days have no announcement to fall back on. So they are backed up and restored, never regenerated, and the restore runbook now says so explicitly next to the list of records it rebuilds instead.

A record cannot be half-rebuilt, and the treatment is decided per record, so keeping both kinds in one place would have guaranteed one of them the wrong handling during exactly the incident the distinction exists for.

A second benefit falls out of the separation. Where a day is described by both sources, the announcement wins — it is immutable, while the recomputation can drift. With two separate records that preference is a property of **how the read looks things up**, which nothing can violate. Had they shared one record it would have been a rule about which write happened last, which is the kind of guarantee that holds until it doesn't.

**Every recomputed day carries whether the platform had committed to it.** The recomputation returns figures and no such marker, and the days it covers are mostly from the period before any commitment was made — so storing the figures bare would republish estimates as though they were emissions, in the flattering direction. That is precisely what the marker on the announcement exists to prevent. The pass resolves the commitment start once and stamps every row, and it **refuses to write anything at all** if it cannot establish that — a backfill that guesses is worse than no backfill. There is a documented trap here that it honours: the "not yet committed" state is recorded as a zero, and reading that as "everything is committed" would mark the entire pre-commitment history as real emission.

Two figures are stored as *unknown* rather than zero, because the recomputation genuinely does not return them. A zero margin is a real and different thing, and this surface has been caught by that ambiguity twice already.

**Why an operator-run pass rather than something automatic.** It needs to read the chain, and it has to be sequenced by hand relative to a role handover — run it before, or the answers it captures are already the wrong ones. The indexing service is deliberately read-only and holds no keys, and adding a privileged write path to it for a one-time job would be a change in posture out of proportion to the task. It emits ordinary statements, applied with the same command the rest of the restore runbook uses, and it produces **nothing at all** on failure so a redirect cannot leave a half-written file.

Re-running it will not overwrite what is already stored. The first capture is the one taken while the inputs were intact; correcting a row afterwards is a deliberate act, not a side effect of running a command twice.

**The same mistake three times, so the third fix removed the possibility.** Adding a second source of days meant updating everything that reads days — and I updated them one at a time as each was pointed out: first the window that decides which days to show, then the lifetime totals, then the recovery tool that has to recognise the new record. The first two are the same defect. So the two sources are now merged **once**, and every consumer reads the merged result; there is no longer a second place that also reads days and can be forgotten. Which source wins where both describe a day lives in that merge and nowhere else.

**And then the claim itself turned out to be false.** Having said every reader now used the merged view, one still did not — the runway estimate was still reading the announcement records directly, so a window containing recomputed days came out short, and a dataset made entirely of them had no window at all. Asserting that a fix is complete is not the same as checking, and I asserted. The check is one line: list every direct read of either record and confirm only the merge remains.

The same round corrected something the merge had got wrong in the opposite direction. It was *adding* absorption from both sources for a day they both describe — but the recomputation reads the live running totals, which already include every historical credit the announcements folded, so an ordinary replay counted the same value twice. The snapshot is not merely preferred there, it is complete: credits always land on the current day, and a late report for an already-closed day is refused, so nothing new can arrive for a day the recomputation has covered. The merge was fixing a case that cannot happen and creating one that can.

**The recovery tool would have rejected every backup taken after this ships.** It treats records it does not recognise as hostile and refuses to convert the archive at all — so registering the backup without registering the restore would have left the documented recovery path unusable, silently, until someone needed it. It now knows the record's shape, its key, and which era it appears from; the commitment marker is in the required-column set, because an archive missing it would restore every pre-cutover day as *uncommitted* and republish estimates as emissions.

**Three smaller hardenings, each about a plausible operator slip.** The chain identifier was only a label, so pairing a valid endpoint for one network with another network's id would have written every row under the wrong chain — and because a re-run does not overwrite, unrepairably. It now compares against the endpoint before reading anything. A malformed day range left the start as *not-a-number*, which made the loop run zero times and the pass exit **successfully** reporting nothing scanned; it now refuses. And because every deployment applies migrations *after* deploying, the new query would have failed for the length of the rollout — it now falls back to the announced-days-only view rather than failing the whole endpoint over an additive change.

**Four more, and two of them were the same rule applied to one side only.** The runway numerator takes the larger of what a chain reports about itself and what this consumer observed — and that rule had been applied to the local side and not the cross-chain side, so a history made entirely of recomputed days dropped every recovered cross-chain credit. The recomputation also discarded days that had absorbed value but were never finalised, on the reasoning that there was no pool to preserve; for a day predating this consumer's coverage the recomputation is the only source for that attribution, so discarding it lost the attribution permanently. Those days are now kept, with no pool and their real credits.

The pass also reads every day against **one pinned block** rather than whatever is current when each read runs. A handover landing mid-scan would otherwise capture early days before the overwrite and later days after, and because a re-run does not overwrite, that mixed history would be preserved as the record — a half-corrupted result with nothing to signal it. And the documented invocation redirects into a directory a clean checkout does not have, so it failed before starting.

**Restoring a backup now checks what the rows say, not just that the columns exist.** The amount fields are text, so a non-numeric value imports without complaint and then throws when the page reads it — taking down the whole series for that chain — while a plausible wrong number falsifies published history instead. Values are validated before any destructive batch is generated, including the commitment marker, and including the combination that says a day was both unfinalised and committed, which the writer never produces.

The related gap: an archive that omits this record entirely produced only a warning, so a selective restore left whatever the live database already held — possibly the very rows the restore was meant to remove. It now emits an explicit clear. An archive that legitimately predates the record loses nothing; a truncated one loses the rows it was hiding.

**Reconciling cross-chain stock had to become per-source.** Taking the larger of "what every chain reported" and "what we observed in total" compares two sums, and a chain present only in the recomputed history is dropped whenever another chain's reported figure dominates the comparison. Each source now contributes its own reported figure, and whatever the observed total holds beyond what those reports account for is added as stock no report covers — which needed the platform to start recording, per source, how much of each report was actually attributed.

**The two sources are now combined by taking the larger of each component, in every case.** Adding them double-counts, because the recomputation reads running totals that already include what the announcements carried. But the recomputation can also be *stale* for a day that never finalised — a delayed cross-chain report is still accepted for such a day, so the announcements may know more than the capture did. The maximum is right in both directions, and making it conditional on whether the day was finalised would have distinguished nothing any input can produce.

**Three more hardenings on the operator pass.** Day numbers are now required to be *safe* integers with a bounded span — the previous check accepted a value large enough that incrementing it does nothing, which would have looped on one day forever while consuming request quota and emitting nothing. Output goes to a named file written under a temporary name and renamed only after a complete run, because a shell redirect truncates its target before the process starts and the previous capture is precisely the thing that cannot be recreated. And each row now records which revision of the pass produced it — the schema comment already promised that provenance and the schema did not deliver it, which matters because these rows are non-reproducible and the first write wins.

**Restoring now also checks that the commitment marker agrees with the sentinel it derives from**, not merely that both are well-formed numbers: a row claiming commitment under a sentinel meaning *never committed* would republish an estimate as real emission. And the validation runs *before* anything is written to the staging area, so refusing a hostile archive no longer overwrites a previous known-good staging output on its way out.

**The runway estimate now refuses rather than guessing, and that is the honest end of four rounds of trying.** Combining recomputed and announced history for a lifetime cross-chain figure kept producing a number that was wrong in a new way each time: first it omitted this deployment's own pre-launch stock, then every other chain's, then it dropped a chain present only in the recomputed history, then it under-counted whenever the two sources each held credits the other did not. Every fix was locally right and the next case broke it, because the cross-chain total for a recomputed day is summed across chains before it is stored — the information needed to reconcile it simply is not there.

So when a recomputed day carries cross-chain absorption, the figure is reported as unavailable with a stated reason, and every component it would have been built from is still published. That is the same rule the rest of this surface already follows: an absent number beats a plausible wrong one. The refusal is deliberately narrow — a recomputed day is not disqualifying, only an undecomposable cross-chain total — and a test pins that so it cannot quietly widen into "the estimate never works". Making it exact is a change to what the recomputation records, not to how the arithmetic is arranged, and is tracked separately.

**A rule written in one file was broken in the next round in that same file.** The record noting which derived tables have been rebuilt carries an instruction to bump its version whenever a new one is added — and adding a column to an existing one is adding one. Without the bump, a database that had already rebuilt would skip the new work and then treat every historical credit as unaccounted, adding it a second time. The version is bumped, and the instruction now says that a column counts.

**And the rollout tolerance was applied to one query and not its neighbour in the same expression.** Deployments apply migrations after deploying, so during a rollout the older table shape is what the new code meets; one of the two parallel reads handled that and the other would have failed the whole request. Both do now.

**One check had to learn a new shape.** The repository requires every stored record to declare how it should be treated on restore, and it finds them by looking for writes inside the services. This one is written by an operator pass, so it would have been flagged as orphaned forever — and a check that always warns is a check people stop reading. It now accepts an explicit declaration naming the writer and why it is not a service, and fails if that declaration points at a script that does not exist.
