## Keeper machine — builds no longer starve the keeper (PR #<n>)

The keeper's late-acknowledgement pass missed its read deadline on about one tick in twenty. Most misses fell on all three chains in the same tick, and the next tick always caught up. The machine's own logs gave the cause: 60 of the 63 failing ticks in one day ran while the machine was building a new keeper release. The machine is small (about 1 GB of memory), and it rebuilt the keeper after every merge to the main branch, about 32 times a day, whether or not the merge touched the keeper. During a build, ticks started several seconds late and 37% of them missed the deadline. Outside a build the miss rate was 0.2%. No RPC provider was at fault.

Two changes keep builds out of the keeper's way. First, each release now records the files its bundle was made from. The machine builds a newer commit only if that commit changes one of those files, the deploy kit, a config file that decides how they are read, or a root-level file such as the lockfile. Any other commit would rebuild the same bundle byte for byte, so the machine stays on the release it has and logs that once. About half of recent merges are like this. Anything the comparison cannot read counts as a build, so a mistake costs a few minutes of building rather than leaving the keeper on old code. As a result, the release the keeper reports can be older than the main branch. Second, the updater and its build now run at the lowest CPU and disk priority, so the keeper always comes first.

Nothing here moves funds or changes what the keeper does on chain. The deploy model and its trust statement are unchanged: the machine still builds exactly the commit it deploys, from its own checkout. Closes #2651.
