## Thread — the Offer Book states a borrow request's committed collateral range (PR #2413)

A borrow request can commit a collateral range: a floor, and a ceiling up to which a matched fill may lock more. The Offer Book card used to show only the floor, worded "at least X" since #2378 because the market data did not carry the ceiling. The indexer now records both the effective ceiling and the part that earlier matched fills have consumed. Effective means a single-value request is stored with its ceiling equal to its floor, so readers never meet the chain's zero sentinel. The values are written when an offer is created, when its details are refreshed and when it is amended. A match does not read the borrower offer inside the scan: it marks the request's used amount as unread, and the detail-refresh lane reads it, so a burst of matches cannot spend the scan's request allowance. Under borrower-side partial fills a request stays open with part of its range used, which is why the borrower side is tracked at all.

The card now states the range, says that funding the request directly locks exactly the floor (the rest goes back to the borrower), and says a matched fill can lock more, up to the ceiling. A request that earlier fills have part-used states exactly what is still committed and how much earlier fills consumed (a running total, not what is locked today, since a resulting loan may have settled), and says only a matched fill can use the rest; when what is left is below the floor every fill must lock, it says no further fill can use it until the request is amended or cancelled. A request whose ceiling equals its floor is NOT shown as an exact figure: it commits exactly that amount, and funding it directly locks all of it, but a matched fill locks only what the lender requires, so the card says both; it does not say where the unused part goes, because that depends on whether the deployment allows partial fills (refunded at the match if not, kept committed for later fills if so). Until the indexer has read a request's ceiling and the part already used (older rows are re-read by the detail-refresh lane, oldest first), the card keeps the honest "at least X". The loan-to-value line keeps marking every borrow request "a fill of another size can differ", for the same reason: knowing the ceiling narrows the range of outcomes, it does not remove the matched-fill path. For a request earlier fills have part-used, it gives no ratio at all and says why: each further fill sets its own amounts, so there is no single pair to take one at.

The detail-refresh lane now also keeps an offer's recorded holder when its position-token owner cannot be read, instead of writing the creator back over a transferee; only a row with no recorded holder falls back to the creator.

Re-reading every older active offer is a large backlog for the first ticks after the migration. The refresh lanes now run last in each scan, after it has recorded its progress and finished every once-per-scan step, so however much they spend they can only delay heal work, never stall the scan; they also stop starting rows once the invocation's request or database-query allowance is nearly used, and pick up the rest on later ticks.

The new columns arrive by a database migration, which the deploy now applies before publishing (#2409). Until it lands, the Worker's schema gate holds scheduled writes, and the offer API keeps answering because it reads whatever columns exist. Closes #2382.
