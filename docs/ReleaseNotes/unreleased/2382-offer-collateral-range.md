## Thread — the Offer Book states a borrow request's committed collateral range (PR #2413)

A borrow request can commit a collateral range: a floor, and a ceiling up to which a matched fill may lock more. The Offer Book card used to show only the floor, worded "at least X" since #2378 because the market data did not carry the ceiling. The indexer now records both the effective ceiling and the part that earlier matched fills have consumed. Effective means a single-value request is stored with its ceiling equal to its floor, so readers never meet the chain's zero sentinel. The values are written when an offer is created, when its details are refreshed, when it is amended, and, for the borrower side, when a match happens. The match write reads the borrower offer's filled amounts at the match's own block, as the lender side already did: under borrower-side partial fills a request stays open with part of its range used, and the old note that skipped the borrower offer predated that.

The card now states the range, says that funding the request directly locks exactly the floor (the rest goes back to the borrower), and says a matched fill can lock more, up to the ceiling. A request that earlier fills have part-used states what is still committed and how much is already locked, and says only a matched fill can take the rest. A request whose ceiling equals its floor is NOT shown as an exact figure: it commits exactly that amount, and funding it directly locks all of it, but a matched fill locks only what the lender requires and returns the rest, so the card says both. Until the indexer has read a request's ceiling and the part already used (older rows are re-read by the detail-refresh lane, oldest first), the card keeps the honest "at least X". The loan-to-value line keeps marking every borrow request "a fill of another size can differ", for the same reason: knowing the ceiling narrows the range of outcomes, it does not remove the matched-fill path.

Re-reading every older active offer is bounded by the Worker's per-invocation request allowance: the refresh lanes run before the scan records its progress, so they now stop while that write is still affordable, and pick up the rest on later ticks. Without the bound, the first ticks after the migration would have spent past the allowance and replayed the same block range.

The new columns arrive by a database migration, which the deploy now applies before publishing (#2409). Until it lands, the Worker's schema gate holds scheduled writes, and the offer API keeps answering because it reads whatever columns exist. Closes #2382.
