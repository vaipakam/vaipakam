## Thread — the keeper's private database on the always-on machine, and the machine as the keeper's only runtime (PR #2497 re-cut)

**The private database on the machine.** The always-on machine reaches the keeper's private database through the same Cloudflare D1 interface and credentials it already uses for the shared one. The database id is fixed in the code, so a wrong setting cannot point the machine at another database. A Worker deploy applies the private migrations and refuses to publish until the one-time copy is recorded. The machine has no deploy step, so it asks the same two questions before every tick. Does the private database record every keeper migration? Does the copy's record still match the old shared tables? Until both answers are yes, the tick does nothing and logs why. The full check runs on every tick, so a keeper that writes the old tables later stops the machine on its next tick. The machine never applies migrations or copies tables itself; both stay with the keeper's deploy and its copy command. The runbook gives the order: pause the machine's updates, stop the keeper, migrate, copy, resume.

**A redeploy resets the keeper's own state.** When a chain gets a fresh Diamond, its loan numbers and day records start again. A row the keeper kept from the retired Diamond could make a reused loan number look already alerted, or a day look already reported. So the keeper now remembers which Diamond each chain's private state belongs to, as the indexer does for its tables. When a chain's Diamond changes, the keeper clears that chain's rows from every private table that is not already keyed by Diamond. It does this only once the indexer has adopted the same Diamond, so the keeper never reads the new Diamond's numbers against the old one's shared rows. It deletes, checks each table is empty, and only then records the new Diamond, so an interrupted reset is simply done again. A failed read stops the tick rather than guessing.

**The machine is the keeper's only runtime.** The keeper's Cloudflare Worker no longer runs keeper work on a schedule. A scheduled run that arrives anyway, for instance from a schedule restored by hand, does nothing and says why. The Worker stays deployed only as the private database's migration applier.

**One slow pass no longer holds back the others.** On the machine, a pass that is still running when its next minute comes is not started again, but every other pass due that minute runs on time. Before, the whole minute was skipped, so one slow pass could delay the liquidator. Sends from different passes stay in order because they all go through the keeper's per-account send queue. The machine also renews the runner lease itself, every minute that any pass is still running, even when that minute's tick is declined. So another runner can never take over while a long pass is still sending. Refs #2496.
