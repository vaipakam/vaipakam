## Thread — Keeper machine: the private database, checked the way the Worker deploy checks it (PR #2497)

The keeper's private database now works on the always-on machine as well as on the Worker. The machine reaches it through the same Cloudflare D1 API and credentials it already uses for the shared database. Its id is fixed in the code, as the Worker's is, so a wrong setting cannot point it at another database. A Worker deploy applies the private migrations and refuses to publish until the one-time move of the keeper's old tables is recorded. A machine has no deploy step, so before each tick it asks the same two questions. Does the private database record every keeper migration? Does the move's record match the old shared copies? Until both answers are yes, the tick does nothing and logs why. A machine that picks up the new build before the move therefore stops, instead of starting from empty state and repeating work its old log already recorded. The machine never applies those migrations or moves those tables itself. Both stay with the keeper's deploy and its cutover script, so each database keeps one applier. The runbook gives the order: pause the machine's deploys, stop the keeper, migrate, run the cutover, resume. After the first check passes, the machine keeps re-reading the old shared tables on every tick, so a keeper that writes them later stops it on its next tick. The keeper's delivery-proof pass also no longer falls back to rebuilding an old remittance's day list from the live per-day marks, which a release can rewrite. A remittance without its recorded day bitmap is now logged and left gated, never guessed. Two of the keeper's passes now remember how far back their finished work reaches, and never move that mark past what the indexer has completely recorded, so a block still being written is read again. Finished records behind the mark are pruned, which keeps them bounded. A failure in the late-delivery acknowledgement step no longer stops the same tick's ordinary acknowledgements. The sanctions screen now also covers every wallet that has ever held a loan position, not only the first and the latest holders. It no longer moves past a wallet whose observation it could not send in that tick. Refs #2496, #2516.
