## Thread — the keeper's private database on the always-on machine, and the machine as the keeper's only runtime (PR #2497 re-cut)

**The private database on the machine.** The always-on machine reaches the keeper's private database through the same Cloudflare D1 interface and credentials it already uses for the shared one. The database id is fixed in the code, so a wrong setting cannot point the machine at another database. A Worker deploy applies the private migrations and refuses to publish until the one-time copy is recorded. The machine has no deploy step, so it asks the same two questions before every tick. Does the private database record every keeper migration? Does the copy's record still match the old shared tables? Until both answers are yes, the tick does nothing and logs why. The full check runs on every tick, so a keeper that writes the old tables later stops the machine on its next tick. The machine never applies migrations or copies tables itself; both stay with the keeper's deploy and its copy command. The runbook gives the order: pause the machine's updates, stop the keeper, migrate, copy, resume.

**A redeploy resets the keeper's own state.** When a chain gets a fresh Diamond, its loan numbers and day records start again. A row the keeper kept from the retired Diamond could make a reused loan number look already alerted, or a day look already reported. So the keeper now remembers which Diamond each chain's private state belongs to, as the indexer does for its tables. When a chain's Diamond changes, the keeper clears that chain's rows from every private table that is not already keyed by Diamond. It does this only once the indexer has adopted the same Diamond — and "adopted" means the indexer has finished its own reset for that chain, not merely written the new Diamond down — so the keeper never reads the new Diamond's numbers against the old one's shared rows. The one-time copy writes the keeper's first record from that same rule, and refuses to complete for a chain the indexer has not settled on; a keeper that finds private rows for a chain with no record stops rather than guessing which Diamond they belong to. It deletes, checks each table is empty, and only then records the new Diamond, so an interrupted reset is simply done again. A failed read stops the tick rather than guessing.

**The machine is the keeper's only runtime.** The keeper's Cloudflare Worker no longer runs keeper work on a schedule. A scheduled run that arrives anyway, for instance from a schedule restored by hand, does nothing and says why. The Worker stays deployed only as the private database's migration applier.

**One slow pass no longer holds back the others.** On the machine, a pass that is still running when its next minute comes is not started again, but every other pass due that minute runs on time. Before, the whole minute was skipped, so one slow pass could delay the liquidator. Sends from different passes stay in order because they all go through the keeper's per-account send queue. The machine also renews the runner lease itself, every minute that any pass is still running, even when that minute's tick is declined. So a run of declined ticks no longer lets the lease lapse under a long pass; a renewal that fails is logged and tried again the next minute.

**While a redeploy is being adopted, the keeper waits on every chain.** A chain runs only while the indexer has settled on the same Diamond the keeper is configured with, and the keeper checks that on every tick, not only when its own record changes. So while the indexer has not yet adopted a chain's new Diamond, is still clearing the old one's rows, or has moved to a Diamond the keeper's build does not name yet, every tick declines with a line saying it is waiting, for all chains, liquidations included. That gap normally lasts only until the indexer's next run after its own deploy, or the keeper's next update. A decline that persists means one of the two has not picked up the redeploy.

**A pass already running when the indexer moves stops acting too.** A pass can run past the minute that launched it, and the indexer can adopt a new Diamond in that time. From then on the pass holds the old deployment's view of the chain while the shared records belong to the new one, so anything it did next — a liquidation, an alert, a stored notification — could land on a loan number the new Diamond has given to someone else. The keeper now re-checks the indexer's adoption at the moment of every effect: before it signs a transaction, before it sends an alert, and before it writes a record, in whichever pass. If the indexer has moved, the effect is refused and the pass reports it like any other failure; reading, which changes nothing, is not checked. Refs #2496.
