## Thread — Keeper machine: the private database, checked the way the Worker deploy checks it (PR #2497)

The keeper's private database now works on the always-on machine as well as on the Worker. The machine reaches it through the same Cloudflare D1 API and credentials it already uses for the shared database. Its id is fixed in the code, as the Worker's is, so a wrong setting cannot point it at another database. A Worker deploy applies the private migrations and refuses to publish until the one-time move of the keeper's old tables is recorded. A machine has no deploy step, so before each tick it asks the same two questions. Does the private database record every keeper migration? Does the move's record match the old shared copies? Until both answers are yes, the tick does nothing and logs why. A machine that picks up the new build before the move therefore stops, instead of starting from empty state and repeating work its old log already recorded. The machine never applies those migrations or moves those tables itself. Both stay with the keeper's deploy and its cutover script, so each database keeps one applier. The runbook gives the order: pause the machine's deploys, stop the keeper, migrate, run the cutover, resume. After the first check passes, the machine keeps re-reading the old shared tables on every tick, so a keeper that writes them later stops it on its next tick. The keeper's delivery-proof pass also no longer falls back to rebuilding an old remittance's day list from the live per-day marks, which a release can rewrite. A remittance without its recorded day bitmap is now logged and left gated, never guessed. Two of the keeper's passes now remember how far back their finished work reaches, and never move that mark past what the indexer has completely recorded, so a block still being written is read again. Finished records behind the mark are pruned, which keeps them bounded. A failure in the late-delivery acknowledgement step no longer stops the same tick's ordinary acknowledgements. The sanctions screen now also covers every wallet that has ever held a loan position, not only the first and the latest holders. It no longer moves past a wallet whose observation it could not send in that tick. The indexer's progress mark is now read before the work it bounds, so the done mark can never pass work the keeper has not seen. Each finished record also stores the block it came from, so cleanup depends only on the done mark and a cleanup that fails is simply done again on the next tick. The delivery-proof pass now reads a packet's reservation on the chain and contract the packet itself says sent it, not on whichever Diamond is configured today. That matters after a fresh redeploy, when remittance numbers start over. The sanctions-hold pass now records a clean result on-chain for a wallet whose old evidence is still stored, once the oracle answers clean. Without that, a later flag could have been read as one continuous hold. Its per-tick transaction budget now grows with the number of held wallets, so each one is observed within six hours, up to a fixed ceiling. Past that ceiling the operators get an alert instead of silently lapsing chains. A later round replaced how the delivery-proof and late-acknowledgement passes keep track of their work. Each pass now finds new items by walking the event log forward a page at a time, never past what the indexer has fully recorded, and keeps the items still open in a queue. An item leaves the queue only when the chain shows it finished, so one that can never finish no longer holds the log read back, and neither read grows with history. The machine's check of the one-time move now runs in full on every tick, which catches even a same-second rewrite of an old table. The sanctions pass now counts every kind of write in its budget and reserves the share its observations need. On the machine, a pass that is still running when its next minute comes is no longer restarted, but every other pass due that minute now runs on time. Before, the whole minute was skipped, so one slow pass could hold back the liquidator. The sanctions pass now sends one observation for every wallet that is due one, held or confirmed, before it spends anything on clean commits or settlement backlogs. Refs #2496, #2516.
