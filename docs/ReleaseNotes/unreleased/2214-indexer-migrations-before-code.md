## Thread — indexer: migrations before code, and a schema gate for the routes that skip them (PR #2409)

The indexer's deploy now applies its database migrations FIRST and publishes the new Worker only if they applied. The apply step lives in one place, the indexer's migrate script. The deploy scripts of all three Workers that share the database (indexer, keeper, agent) run it before publishing, so whichever Worker an operator publishes first, the schema lands first. The deploy scripts (single-chain, testnet, mainnet) call those package scripts. Before publishing, the deploy confirms in the database that every migration the build carries is recorded, so an apply that ends without applying (a declined prompt, a partial run) stops the publish instead of passing on its exit status. The deploy takes no arguments; a dry run has its own command that never touches the database. They used to publish and then migrate, so on every release with a migration, new code ran against the old schema for the length of the gap — and indefinitely if the migration step failed, because nothing rolled the Worker back. #1149 was that window in production: every scan failed on a missing column and the chain's reading position held until someone read the logs. #2214 asked the question and was closed without the change; this makes it.

The indexer also deploys automatically on every merge through Cloudflare Workers Builds, and that route's deploy command is dashboard configuration the repository cannot see or pin. So the Worker now carries a schema gate as well. The build lists every migration it carries (the whole set, so a migration that fills an old numbering gap cannot slip past); until the database records all of them as applied, every scheduled tick and every chain pass declines, with a log line naming the missing migration and the command that applies it. Nothing is scanned, pruned or swept, and the reading position stays put. On the first tick after the migration lands, ingest resumes by itself, with no redeploy and no cursor repair. A new check in the indexer's typecheck fails CI unless that list matches the migrations directory exactly. The keeper and agent have no gate of their own yet (their automatic deploys are tracked in #2410). The gate holds scheduled writes only: a read-API route that reads a brand-new column still has to tolerate the older schema itself, and the docs say so.

Operator follow-up, recorded in the indexer README: set the Workers Builds deploy command to the package deploy script, with a build token carrying D1 edit rights. Then the automatic deploy migrates first too, and the gate becomes a backstop. Until that is set, a merge that adds a migration pauses scheduled ingest until someone applies it. This is the prerequisite for #2382 and #2383, both of which add indexer columns.
