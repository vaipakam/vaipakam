## Thread — Sanctions delister bot, testnet first (PR #2567)

The delisting side of the sanctions list now has its unattended service. Every hour it reads each configured chain's delisting timelock and moves every pending proposal on as far as it can: it clears away proposals whose bot key the owner removed, withdraws its own proposals that can no longer complete (an address the Safe vetoed, one RedStone flags, one already delisted another way, or one OFAC's newer file no longer delists), moves its own proposals onto a newer publication once it has re-checked every address in them, and after the waiting window requests RedStone's answer over Chainlink CCIP where RedStone is on another chain (only once it can reach that chain to relay the answer, since each request costs a fee), relays the answer back, and completes the proposal once the timelock reports it ready. Every step that moves a proposal toward a delisting (requesting an answer, relaying it, completing the proposal) is taken, whoever made the proposal, only after a fresh reading of OFAC's files in that same state supports delisting every address the proposal names. A failed, older or newer download, two files that disagree, a same-day reissue the adder will not apply by itself, or a list part-way through an update, and none of those steps is taken; nor is any while the timelock is not a remover of the list, so revoking that role stops paid requests and relays as well as new proposals. Another proposer's proposal naming an address the files do not support is never moved on, and is reported for the Safe to veto. It then proposes the remaining delistings, and only those that both of OFAC's exports support: the advanced file the list records must no longer contain the address, and the plain SDN.XML, read by its own parser, must not mention it anywhere. The two files must be the same publication and list the same addresses, neither may carry a digital-currency value it cannot read as an address (one may be a damaged copy of an address being delisted, so while one is there every delisting waits for a person), the number of delistings must match what the list itself declares outstanding, and addresses already proposed, vetoed by the Safe, or flagged by RedStone today are left out. Anything only one file supports, or that RedStone flags, is named in the report and left for the Safe. With no RedStone check configured on a chain, nothing can complete there, so it proposes nothing and says the delistings await the Safe.

OFAC's files are downloaded only when a chain has publication work, and a chain whose state has not changed is re-checked once a day, so a delisting the Safe vetoed does not cost a 150 MB download every hour. Only a conclusive check of a chain the run left untouched is remembered: a failed download, two files caught either side of a new publication, or any transaction sent (included is not yet final) means the next hour checks again. The key must be the timelock's proposer and nothing else: not the timelock's owner, and not the adder, remover or owner of the list on any chain it has an RPC for, the chain it relays RedStone's answers from included, checked before the key is used there at all. The timelock must serve the list the release records; otherwise that chain is refused. Every transaction is simulated before it is signed, recorded by hash before it is broadcast, and reported as included, reverted, refused by the node (only when the node names why and answers that it does not hold it), failed or of unknown outcome; one failed step never stops the others (a candidate check that cannot be read proposes nothing and leaves every other step to run), except that after a transaction of unknown outcome it sends nothing more on that chain that run, so a later one cannot take its nonce; anything that did not land is retried next run. A run in which a failure put off work a chain needed, such as no conclusive reading of OFAC's files, is reported as not done and fails the service, so it shows among failed units; waiting for a window, for RedStone or for the adder does not. The RPC of every chain it touches, the attestor's included, must serve that chain. Reports go to the journal every run and to the ops chat when something was sent, failed or needs a person, a refusal before any chain was read included, repeated once a day while a condition lasts; a chat message too long for Telegram is cut, and the journal keeps it whole. Its state files are caches only: deleting them costs a download, never a wrong action. A state file that cannot be written, or an unexpected error on one chain, is reported and fails the service, but never stops the report of what the run sent; the adder records a failed write of its run record the same way.

The adder and the delister now install together from one release of a named commit, with one installer, so they always read a publication with the same parser. Each keeps its own key, settings file, dynamic user, memory cap and units; the kit moved from ops/sanctions-adder to ops/sanctions, and a machine that ran the adder-only installer is moved over by the new one. What both services share (the chain table, the key check, how a file is kept, how a transaction is sent, the ops alert and secret redaction) now lives in one module, and both now say when a node refused a signed transaction, or when one was included and reverted, instead of calling it possibly broadcast. Both OFAC parsers' delisting witness now counts an address split across pieces of a value's text, such as a CDATA section or a comment inside it, as still mentioned. The delister's settings template uses exactly the names of the file already created on the keeper's machine.
