## Thread — Delivery-proof alerts on every mirror (PR #2599)

The keeper's delivery-proof pass, which indexes or proves each reward budget delivery on every mirror so the day-delivery gate never holds a funded day for a manual step, now tells the operator when that work is not getting done. It already runs on the two testnet mirrors (Arbitrum Sepolia and BNB Testnet) but reported only to its log, and the governance runbook said to watch the log because the alerts were not built.

There are two alerts, both sent to the operations chat and kept separate per mirror. The first says that a delivery has arrived but is still not whole more than ten minutes later, which is one full scan after the first scan that could have reached it. It names each such delivery, oldest first, with when it arrived. A delivery the keeper has just worked on counts as whole only when a fresh read after its transactions shows it whole, never because the transactions went through: admitting a rollout-era delivery, for example, only opens the epoch its days are indexed into on a later run. The alert clears only after a run that looked at every open delivery on that mirror; a run that could not read some delivery, or ran out of time before reaching it, may raise the alert but never clears it, and then says "at least" that many, oldest of those it could read, rather than presenting a partial count as the whole. The second says that a proof or index call was refused by the contract, naming the delivery, which of its days the call covered, and the contract's reason. A delivery proven in chunks is held back only by the chunk that was refused, since its other chunks prove on their own, while a list indexed page by page is held back from the refused page on, and the alert says which. A call that never reached the contract, such as a provider timeout or outage, is not a refusal: it is not reported, and the next run tries again. Every refusal of a run goes out in one message, so many refusals cost one send rather than one each; it names as many as fit, counts the rest, and the keeper's log names every one. "Already indexed" and "already admitted" are never failures, because another caller or an earlier run got there first; that holds for a transaction that reverted after being mined too, which is checked again against the state it left before anything is reported. That alert clears once the delivery is whole, once a later run's calls for it all go through, or once the delivery is no longer open work at all, so an alert whose clearing was missed never stays open after the queue moves on. A refusal is reported even when the run is out of time, or when updating the work queue afterwards fails, because a later run may succeed and could not report it, while clearing an alert and the not-whole report wait for the next run, which can measure them again. A refusal for a delivery that the same run then found whole is not reported, since nothing is held back. Error text from the network is never copied into an alert, because it can carry the provider address and its key.

The issue asked for the user-facing bot; these alerts go to the operations bot instead, because the people who act on them are the operators. The runbook now says what "verified on a mirror" means before the irreversible day-delivery gate may be armed there: deliveries indexed or proven within those ten minutes, and neither alert open. The end-to-end scenario against a local chain follows in its own change. Part of #2516.
