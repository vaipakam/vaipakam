## Thread — the keeper gets its own private database for its operational state (#2450)

**What changed.** The keeper now keeps its own operational state in a second Cloudflare D1 database that only it can reach, alongside the shared database it already used. The private database holds seven tables: the health-factor band each at-risk loan was last seen in, the commitment-report scan positions and finished-day markers, the remittance-acknowledgement scan position and attempt log, the record of which Diamond each chain's state belongs to, and the one-time copy's completion record. Its schema now lives with the keeper.

**What stayed shared, and why.** A table moves only if nothing outside the keeper reads it. The in-app inbox, user alert thresholds and their notification records, Telegram links, the oracle snapshot and liquidity-confidence records, the reconciled-day records the indexer writes, and everything the indexer owns all stay in the shared database. The inbox rows the keeper files for a health-factor band crossing still go to the shared inbox; only the band memory behind them moved.

**Why a separate database.** Database access is granted per database, not per table. On the shared database the indexer and the agent could write any keeper record, and some of those records tell the keeper that work is finished and can be skipped. In the private database, nothing but the keeper can write them.

**How it is kept honest.** The keeper's code cannot send a private-table query to the shared database, because the two connections are distinguished at compile time. The one statement that used to read both kinds of table at once now reads each database separately and behaves exactly as before. The keeper's tests build the shared database without the moved tables, so a query sent to the wrong place fails rather than quietly passing. A test refuses any future shared migration that recreates or alters a moved table; dropping the old copies is the only change it allows. The repository checks recognise the private database: only the keeper may bind it, only under its own name and identity, and never as a second connection to the shared data. A maintenance build drops both connections, and the keeper skips its whole run if either is missing.

**Moving the live rows, once.** Five of the tables already hold live rows in the shared database. A keeper starting from empty copies would re-send acknowledgements it has already paid for and re-alert borrowers it has already warned, so the rows are copied once, with the keeper stopped. The copy command copies all five tables. It checks that each matches on both sides by row count, latest write time and a fingerprint of every row, and only then records that the copy is complete. It refuses to run over a copy it has already recorded. The keeper's deploy applies the private schema itself, because the keeper is that database's only writer. It also refuses to publish while the shared copies hold rows and no matching record exists. After the copy, rows that have only gone are accepted, since the indexer's own reset after a redeploy deletes a chain's rows. A row that is new or changed, which only a keeper writing the old copy could cause, still stops it. The old shared copies are dropped later, in a release of their own (#2560). The deployment and restore runbooks carry the steps.
