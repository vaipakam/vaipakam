## Thread — the keeper gets its own private database for its operational state (#2450)

**What changed.** The keeper Worker now binds a second Cloudflare D1 database, private to it, alongside the shared one it already used. Eight tables of keeper-only operational state live there: the health-factor band each at-risk loan was last seen in, the commitment-report scan positions and finished-day markers, the remittance-acknowledgement scan position and attempt log, the record of which operator alerts were already sent, the keeper's record of finished work (below), and the cutover's completion record. The keeper's private schema now lives with the keeper, and the operator-alert table that the sanctions-hold observer introduced is created there only — it was never applied to the shared database, so that earlier migration was withdrawn rather than shipped.

**What stayed shared, and why.** A table moves only if nothing outside the keeper reads it. The in-app inbox, the user alert thresholds and their notification records, the Telegram links, the oracle snapshot and liquidity-confidence records, the reconciled-day records the indexer writes, and everything the indexer itself owns all stay in the shared database. The inbox rows the keeper files for a health-factor band crossing still go to the shared inbox; only the band memory behind them moved.

**Why a separate database.** The project already keeps internal operator-alert state out of the shared, user-facing database, and the alert record is exactly that kind of state. There is a second gain: database access is granted per database, not per table, so on the shared database the indexer and the agent could write any keeper record. Some of those records tell the keeper that work is finished and can be skipped. In the private database, nothing but the keeper can write them.

**How it is kept honest.** The keeper's code cannot hand a private-table query to the shared database: the two connections are distinguished at compile time. The one statement that used to read both kinds of table at once — pruning band memory for loans that have closed — now reads each database separately and behaves exactly as before. The keeper's tests now build the shared database without the moved tables, so a query sent to the wrong place fails instead of quietly passing. A test also refuses any future shared migration that recreates or alters a moved table; dropping the old copies is the only change it allows. The repository checks now recognise the private database: it may be bound only by the keeper, only under its own name and identity, and never as a second connection to the shared data. The restore-runbook check confirms each table is cleared in the database it actually lives in. A maintenance build drops both connections, and the keeper skips its whole run if either one is missing.

**Cutover order (at the end-of-programme deploy, not now).** Five of the six tables hold live rows in the shared database today. A keeper starting with empty copies would re-send acknowledgements it has already paid for and re-alert borrowers it has already warned. So the order matters:
1. Apply the keeper's own schema to the private database.
2. With the keeper stopped, run the keeper's cutover command. It copies all five tables, checks that each one matches on both sides, and only then records that the cutover is complete.
3. Deploy the keeper immediately afterwards.
4. Confirm one run used the private database and the old shared copies stopped changing.
5. Only later, once nothing reads the old copies, drop them through a new shared migration.

The keeper's deploy applies its own schema (it is the only writer of that database) and verifies it in the database before publishing, so later keeper migrations need no manual step. Step 2 is one command, run by hand because it needs the keeper stopped, and the deploy refuses to publish until it has run and still holds. Each of the five tables is compared on both sides by its row count and the time of its latest write. Every keeper write stamps that time, so a partial copy has the wrong count, and a write to the old copy after the copy moves the time. The command records completion only when all five match. It refuses to run over a completion it already recorded, because that would replace the new keeper's state with the old copies. The deploy publishes only when that record exists and every shared table still matches it, or when the shared copies hold no rows at all. An earlier version of this check looked at two of the five tables and passed as soon as the private side held a single row, so it would have published after a partial copy. The deployment runbook carries the steps. The restore runbook now creates the private database too. It notes that a restore starts it empty, because the nightly archive never carried these tables. It also clears the band memory in its new home, before the inbox, so an interrupted clear can only re-alert and never go silent.

**Work is kept until the chain says it is done.** Two keeper passes find their work in the shared event log: the delivery-proof pass (every budget delivery a mirror received) and the late-acknowledgement pass (every remittance the canonical chain released). The first read only the last 45 days of deliveries, the second only the newest 50 releases, so a delivery still waiting on its proof, or a release still waiting on its acknowledgement, could fall outside the window and never be handled. Both now read every candidate the log holds and skip only the ones the keeper has recorded as finished. An item is recorded as finished only when a read of the chain shows it: a delivery whose days are all indexed or proven, or a release with nothing left to acknowledge. The record lives in the keeper's private database and is kept per Diamond, so a fresh deployment starts clean.
