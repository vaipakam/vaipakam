## Indexer — a health route that says whether ingest is advancing, and why not (#2469)

When the indexer was published ahead of a database migration, its schema gate correctly paused all scheduled ingest until the migration was applied. The gate said so only in the Worker's logs, so the stall went unnoticed until stale screens did the reporting.

The indexer now answers a read-only health route. For each chain it scans, the route reports the last block it reached and how long ago it got there. It also reports whether this build's migrations are all applied and, if not, names the missing ones. It states facts, not a verdict: what counts as stale depends on the caller, and a chain the indexer no longer scans keeps its last position forever. The route reads only the database, so it still answers when the secrets service, one of the things that can stall ingest, is degraded. Responses are never cached.

A scheduled GitHub check now reads that route every 15 minutes and fails when the Base Sepolia, Arbitrum Sepolia or BNB testnet ingest has not advanced for 15 minutes, or a cursor's timestamp is ahead of the indexer's clock, when the indexer is waiting on a migration (it names the migration and the command that applies it), or when the route can't be read. On the first failing run it opens an issue titled "Indexer ingest stalled", assigned to the operator, and adds nothing more while the stall lasts. It closes the issue with a comment on the first healthy run. A failed run alone is not a dependable alert: GitHub notifies only the account that last edited the schedule, and only if that account has Actions notifications turned on. If the ops Telegram secrets are added to the repository, it also posts once to the ops chat when the issue opens. The check runs on GitHub rather than as a Cloudflare Worker because every Cloudflare scheduled trigger on the account is already taken, and because a watcher inside the indexer could not report the indexer's own crash. Sepolia is not watched: the indexer no longer scans it, so its position stands still for good. A run that fails before it can judge anything opens a separate "probe not running" issue, so the operator is never told ingest is stalled when its state is simply unknown.

The indexer's own deploy now applies migrations before publishing on every merge, which removes the cause of the 0056 stall. This check is the alarm for any other cause.
