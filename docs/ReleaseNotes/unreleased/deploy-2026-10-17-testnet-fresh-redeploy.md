## Thread — Fresh testnet redeploy of Base Sepolia and Arbitrum Sepolia, and the deploy build step stops compiling the test tree (PR #<n>)

The end-of-programme redeploy the build-first work (PR 1 #2459, PR 2 #2489, PR 3 #2521) called for landed on both active testnets. Every chain's storage layout changed across those three PRs, and the protocol's rule for a layout change is a fresh Diamond rather than an in-place facet refresh, so each chain received a new Diamond, Timelock, VPFI lane and reward messenger. The prior Base Sepolia Diamond still held three test offers and two test loans; the deploy was run with the explicit acknowledgement that those stay on the retired Diamond (which remains on-chain and settleable at its old address) and disappear from the indexer and app. Arbitrum Sepolia's prior Diamond held no live state. Both retired Diamonds are recorded in the archive manifest so the custody census keeps reading them. The chain artifacts, the consolidated deployments bundle and the per-facet ABIs in this change are what every Worker and app now reads.

Alongside, the three deploy scripts (testnet tiered, testnet one-shot and mainnet) no longer compile the test tree in their first build step. That step used a bare build, which folds every test file into one compilation unit; this codebase has outgrown that form (a 19 GB compiler run that swapped for an hour and never finished during this deploy). The pre-deploy check had already switched to skipping tests for exactly this reason, and it compiles the test closure a deploy relies on where it is exercised, in the deploy-sanity suite. The deploy scripts now do the same, so the build step compiles only the contracts and deploy scripts a deploy actually touches.

**The indexer now owns deployment epochs.** Review of this deploy found that a fresh Diamond on a running indexer did not start a new epoch: the chain index keyed everything by chain and numeric id, the scan cursor kept advancing past the new deploy block until the new bundle rolled out and then skipped that interval for good, and the retired Diamond's rows stayed where the fresh Diamond's restarted ids would collide with them. The deploy script's row purge was the only enforcement, run outside the indexer, and it failed silently on this deploy. The indexer now records, per chain, the Diamond and deploy block it has adopted; a bundle naming a different Diamond resets that chain's chain-scoped rows (every table keyed by chain, except user-owned support requests and diagnostic captures) atomically with its own completion mark, so the next scan starts from the new deploy block and an interrupted reset is finished rather than left half-done. Which tables reset is read from the schema, not a list, and the one exception list is guarded. A new epoch only ever moves forward: a build whose bundle names a Diamond deployed before the adopted one (a stale branch) is refused loudly and cannot wipe a live chain's index. A pass scans only when its own Diamond is the adopted epoch; a refused or out-raced pass returns without scanning, as a declined pass the ingest loop does not retry, so a retired or losing Diamond can never repopulate rows or move the shared cursor. Ingest health lists a chain from its deployment record as well as its cursor, so a chain whose cursor is absent right after a reset is stated with empty cursor fields instead of disappearing. The ingest health endpoint states the adopted Diamond per chain. The deploy scripts no longer delete rows themselves; on a fresh redeploy they record the retired Diamond in a marker the indexer's own deploy seeds between the schema migration and the publish, so the new code's first pass finds the retired Diamond and resets rather than adopting the new one without a reset. A record a pass wrote on its own, with nothing reset, is marked as adopted without evidence and a later seed may replace it, but a seed never replaces an epoch earned by a reset, so seeding twice cannot reset twice. The reset discovers the chain-scoped tables in one query so it stays within the indexer's per-invocation database budget, and every statement of the reset is guarded by the pass's own claim, so a claim overtaken by a later deployment deletes nothing. For this deploy the retired Diamonds are seeded when the indexer is next deployed from the merged change.

One app unit test (the acceptance-pin sync frames) had copied the live Base Sepolia Diamond address into its fixtures because the receiver refuses any frame not mined against the deployment the build reads. Every one of its cells failed on the new address alone. It now reads the address from the deployments bundle, so a redeploy can no longer break it.
