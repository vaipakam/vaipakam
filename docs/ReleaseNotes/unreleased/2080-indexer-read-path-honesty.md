## Indexer — reads say when a chain is not served, stats are one consistent view, config labels match their capture, and the ingest probe watches what is configured (PR #<n>)

**A chain that is not being served answers "unavailable" everywhere (#1140).** Most indexer reads that name a chain already refused a chain the indexer is not indexing, but eight did not: the recent-loans tape, market discovery, the active offer book, active loans, both stats endpoints, the loan time series and recent offers. They answered such a chain with an empty list or zero counts, which the app shows as "no fills yet" or "no live markets" when the truth is that the chain is not being served. They now give the same "chain not configured" answer as the rest. The single-loan, single-offer, activity, offers-by-creator and match-source routes follow the same rule, so the whole surface behaves the same way. The check now lives in one place, and a test fails if a new route reads a chain without asking it. The app already treats this answer as unavailable, so nothing changes there.

**Stats counts and the block they cite come from one read (#2080).** The loan and offer stats each read their counts and then, separately, the block the indexer had reached, which they report as "current through block N". If ingest landed between those two reads, the counts were older than the block quoted beside them. All of these figures now come from one database transaction, so the counts and the block always describe the same moment. The counts also agree with each other: the ERC-20 and NFT subtotals can no longer exceed the active total.

**Config labels are the ones the values were read with (#2073).** The public protocol-config answer adds field names (such as the treasury fee) to the raw on-chain settings. Those names used to come from whichever version of the indexer served the request. If a contract upgrade had reordered the fields without changing their number, a stored snapshot could be served with real values under the wrong names, and nothing would show it. The snapshot now stores the names it was read with, and the answer uses only those. A snapshot taken before this change shows only the raw values until the next refresh adds its names (normally within six hours, sooner after any governance change). This needs an additive database migration (0067).

**The ingest health probe watches what the indexer is configured to scan (#2498).** The probe kept its own list of chains, so a chain that was switched on or restored in the indexer would be ingested but never checked. The indexer's health answer now lists the chains it is configured to scan: those with a deployment and an RPC binding present. It reads this list without looking up any secret, and says so. The probe watches exactly that list, apart from chains named in an explicit "intentionally idle" setting, which is empty today. If the list is missing, or nothing is left to watch, the probe reports a problem instead of passing.

**Also fixed:** after #2647 moved the agent to a five-minute cadence, three agent tests from #2635 ran on a minute the agent now skips and failed on main. They now run on a minute the agent acts on.
