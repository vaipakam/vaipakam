## Thread — the Diamond's balance must be explained, and the liquidation fallback gets one home (#2141, #1566)

**Problem.** The rule behind #2141 is that, for every asset, the Diamond's balance should be fully explained by what the protocol itself owns. A user's asset may pass through the Diamond inside one transaction, but it must not rest there between transactions. Two kinds of user value do rest there today. When a liquidation or a default cannot swap the collateral, the whole collateral stays in the Diamond until a claim, a cure, an internal match or the backstop resolves the loan. And a swap-to-repay intent moves its lot into the Diamond when it is committed, and holds it there until the order fills or is cancelled. Nothing checked the rule, so a new resting owner could appear without anyone noticing. A hand-kept list of the Diamond's balance owners had already gone stale before.

**A check that can fail.** A new invariant suite drives the loan lifecycle through the paths that can leave user value in the Diamond. These include liquidations and defaults whose swaps all fail, claim retries, in-kind claims, cures, backstop absorbs and internal matches. It runs with an external treasury, the mainnet arrangement. For each tracked asset (a stablecoin, wrapped ether and VPFI) it asserts four things. There is one recorded allowance: on today's code a partial internal match rounds the three fallback slices down separately, so up to two wei per partial leg stay in the Diamond with no owner. The first check allows exactly that much and no more, and slice 2 removes the allowance.

- The Diamond's balance equals the protocol's own ledgers plus the user custody still known to rest there. For VPFI, the ledgers are the recycle bucket, the stranded-token recovery reserve, and the grandfathered borrower-fee custody and rebates. The other two assets have no protocol ledger in this harness.
- The balances the harness never funds stay at zero. These are the buyback and reward budgets, the keeper reward budget, the treasury's own balance and payroll. So a new owner showing up there forces the harness to account for it, rather than hiding inside the total.
- Every vault's tracked balance still covers what is encumbered in it.
- Every action family ran at least once, so a green run cannot be a run that never reached the fallback.

The suite runs with the other invariant suites in the pre-deploy invariant pass. The per-PR CI lane does not compile the invariant suites.

**The strict form waits for slices 2 and 3.** The end state #2141 asks for is a user-custody term of zero. That form is written now and recorded failing on today's code, which proves it can fail. It is switched on for the liquidation fallback when slice 2 puts that collateral in the borrower's vault under a lien. It is switched on for intents when slice 3 makes the fill pull the lot from the vault at the moment of use. Intent commits, fills and cancels already run against a mock of the limit-order contract. The slice-3 fill cells and a fork cell come with slice 3.

**The fallback flows move to one host, with no behaviour change.** The liquidation fallback used to be written out twice: once in the health-factor liquidation and once in the time-based default. Both of those facets are close to the contract size limit. The claim path also carried its own retry swap and its own in-kind split. A new internal facet, FallbackCustodyFacet, now hosts all of these:

- the fallback entry, which both liquidation paths call when every swap route fails;
- the claim's retry swap;
- the in-kind split of the fallback collateral;
- a read view that reports how much of a loan's fallback collateral is vault-held and how much still rests in the Diamond.

Only the Diamond itself can call the three entries that change state. The claim keeps the distribution of a successful retry's proceeds, the retry-attempted mark and the retry event. Every storage write, event and token movement is the same as before, in the same order, and so is every revert that carries a reason; a revert with no reason at all now reaches the caller as an empty four-byte error code instead of no data. The three fallback events keep their exact signatures, so anything listening for them keeps matching. At this step the collateral still rested in the Diamond, so the view reported all of it as Diamond-held; slice 2 of the same release (see the fallback-custody-in-vault note) moves it into the borrower's own vault under a lock, after which the view reports it as vault-held. The split exists so that slice 2 changes one producer instead of two, without growing facets that have no room.

**Refresh together, and how this reaches a chain.** The health-factor liquidation, default and claim facets now call entries that only the new facet carries. The four must be refreshed together: a caller refreshed without the new facet reverts on every fallback entry, retry and in-kind claim. When slice 2 moves the custody, the collateral top-up, repayment and internal-match facets join that set, because every reader of the fallback row must use the same custody source. The owner decided on 2026-10-07 that every chain that runs slices 2 and 3 gets a fresh deploy. So no chain is upgraded in place across this change, and no pre-slice row is migrated. No storage is added. Refs #2141, #1566.

**Spec:** none. The invariant suite is a test, and the host split does not change behaviour. The rule that no user asset rests in protocol custody across transactions enters the functional spec with slices 2 and 3, which do change behaviour.
