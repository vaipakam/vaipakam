## Thread — Automated delisting the Safe can veto (PR #2562)

Delisting a wallet from the platform's own sanctions list can now be proposed by a bot instead of being prepared by hand, without taking the decision away from the Safe. A new delisting timelock is appointed as a second remover of the list. Its bot may propose only wallets the list records, against the OFAC publication the list records, and all its pending proposals together may name no more wallets than that publication declared outstanding. Nothing happens for a waiting window (48 hours by default). During the window the Safe or the admin can cancel, and that cancel is a lasting veto on each wallet: the bot cannot bring a vetoed wallet back until the Safe lifts it. Removing the bot's key from the timelock voids everything it proposed, and anyone can clear those proposals away. A publication's delistings wait until its additions are on the list. When the window ends, RedStone's Sanctions Oracle must also not flag the wallet. Where RedStone runs on the same chain it is read directly. Elsewhere the timelock sends a request over Chainlink CCIP, once the window has ended, to a small companion contract on a chain where RedStone runs; that contract reads RedStone when the request arrives and anyone can pay to send its answer back, without being able to change it. Because the request leaves only after the window, the reading is known to post-date it without comparing two chains' clocks or relying on any value someone could guess; any answer that flags a wallet blocks that request for good. Either way, RedStone's own last-update time must be known and within a week (owner-adjustable), so a frozen oracle cannot wave a delisting through. With no RedStone source configured, automated delisting stays closed and the Safe's own direct delist, which is unchanged, remains the only route. One reading on the timelock reports which of these routes applies, and the deploy script prints it. A new testnet deploy script installs the timelock for the recorded rehearsal list; it configures no RedStone source, so on testnets proposals and vetoes can be rehearsed while delistings themselves stay with the Safe.
