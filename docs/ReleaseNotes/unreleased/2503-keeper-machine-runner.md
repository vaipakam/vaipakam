## Thread — The keeper can run on an always-on machine (PR #<n>)

The keeper can now run as a long-lived process on an ordinary machine as well as a Cloudflare cron Worker. With the schedule restored and the keeper disarmed, every Worker tick was ended by the free plan's 10 ms CPU ceiling, so the keeper could not do its job on Workers at all. The owner decided to move all keeper work to a separate, always-on machine, with the machine to be chosen later. This change does the engineering so that the move is a configuration step rather than a rewrite.

Both hosts run the same code. The minute's work (which passes are due, each pass isolated from the others' failures) now lives in one function that the Worker entry and the machine runner both call. The passes themselves are unchanged, and so are the arming flags. On the machine, the keeper's secrets and settings come from environment variables with the same names as the Worker's bindings, read through the same resolution code. A missing value therefore behaves as it does on the Worker: the affected network or pass drops out. The machine reaches the shared database through Cloudflare's database HTTP API, with an adapter that behaves like the Worker's database binding for the calls the keeper makes. The runner ticks on every UTC minute and passes each pass the minute it is for, so the passes' own schedules (every five minutes, every fifteen, the daily window) behave exactly as under the Worker's cron. A tick never overlaps the next: a tick that runs long makes the following minutes skip, and says how many. On a stop request the runner finishes the tick in flight before it exits, so a pass is never cut off between sending a transaction and recording it.

It ships as a single bundled file, with a systemd unit, a Dockerfile, an environment template and a runbook (`docs/ops/KeeperMachine.md`). A test checks that the template lists exactly the variables the runner reads. Nothing has been started anywhere: the Worker stays unscheduled, and no machine exists yet. Until the single-runner lease lands, which is the next step on #2503, the rule that only one keeper runs at a time is a procedure in the runbook rather than something the code enforces. Refs #2503.
