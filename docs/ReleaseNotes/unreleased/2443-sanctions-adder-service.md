## Thread — Sanctions adder service, testnet first (PR #2557)

The platform's own sanctions list now has the service that keeps it current. Once a day, per chain, it downloads OFAC's publication, keeps the exact file, applies every new addition with the list's adder key, and for a new publication records it on-chain with its delistings declared outstanding for the Safe. It never delists, never rolls back, and refuses every mainnet: the mainnet host is still to be decided. Any refusal by the update tool (a damaged or moved record, an unsupported delisting, an older publication), a list that moved past the finalized block, or a key that is not the adder stops the run before anything is sent. A run counts as applied only once its transactions are final; one that stops part-way says which transactions it already broadcast and whether each is final, included or may still land. Each run reports to the journal and, when configured, the ops Telegram chat (a failed alert is recorded and fails the run), and outstanding delistings are reported on every run until the Safe applies them.

The OFAC parser now reads the publication in pieces instead of holding it in memory. On the 128 MB October 2026 file, peak memory fell from about 500 MB to about 150 MB, with identical results, so the service can share the keeper's 1 GB machine. The service runs as its own systemd units with its own key and dynamic user, a memory cap, and lower CPU and IO weight than the keeper, so it can never take the keeper down. It is deployed by an operator naming a reviewed commit on main, never automatically on merge. A new testnet-only deploy script puts a SanctionsList beside the Diamond's test list as the service's rehearsal target. It appoints the adder and the remover, keeps them distinct from each other and the adder distinct from the owner, and does not change what the Diamond screens against.
