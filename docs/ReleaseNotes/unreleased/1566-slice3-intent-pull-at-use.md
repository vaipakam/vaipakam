## Thread — a swap-to-repay auction's collateral stays in the borrower's vault until its own fill (#1566, #2141)

**Problem.** When a borrower put collateral up for a resolver-filled swap-to-repay auction, the commit moved the auction's lot out of the borrower's vault into the Diamond, where it waited until the auction filled or was cancelled. That broke the owner's custody rule — a user's asset may pass through the Diamond inside one transaction, but must not rest there between transactions — and it was the second kind of user value #2141's attribution suite recorded as resting in the Diamond. It also meant a cancellation had to put the lot back, and a borrower flagged after committing made that return fail, which could block the lender's protection (#658).

**The commit moves nothing.** Committing an auction now records the order and nothing else: the lot stays in the borrower's vault, pledged with the rest of the collateral, and the borrower's fee tier is unchanged. The order still sells exactly the debt-sized lot. Because the commit no longer touches the vault, it no longer screens the borrower as a side effect of that withdrawal: a borrower already flagged can now commit. That is deliberate — the full swap-to-repay is a must-complete close-out that the screen never blocks, and the fill delivers the proceeds through the same freeze-at-destination rules as before.

**The fill takes the lot, and nothing else can happen meanwhile.** The lot leaves the vault only inside the fill that sells it, on the protected path the close-out already uses, so a borrower flagged after committing cannot block the fill that repays their lender. The protocol checks it received exactly the lot (a collateral token that charges a fee on the way fails the fill, and the auction can still be cancelled), records the move with a new event, and refreshes a VPFI holder's tier at the reduced balance. From that moment until the fill's settlement step begins, the protocol refuses every other call into its functions — from a token's transfer callback, from the resolver's own step, from a native-currency payout — so nothing can act on a loan halfway through being repaid; the settlement itself then runs under the protocol's ordinary protection against re-entry. The settlement then pays the debt from exactly the principal the resolver delivered; principal arriving any other way during the fill makes it fail. One trade-off is stated: a resolver cannot settle one Vaipakam auction inside another's fill. An emergency pause now stops fills; an auction stays live until its deadline.

**Cancelling moves nothing.** Every way an auction ends without a fill — the borrower's cancel, the permissionless cancel after the grace period, and the cancellations that liquidation and default force — now only withdraws the order: there is no lot to return. So a borrower flagged after committing no longer blocks any of them, which closes #658. The check that an order was not already filled now reads the limit-order protocol's record of the order's nonce, which is what that protocol actually writes for these orders; the check it replaces could never see a fill.

**How this reaches a chain.** As for slice 2, every chain that runs this change gets a fresh deploy (owner decision, 2026-10-07). An auction recorded under the old custody, its lot already in the Diamond, is refused by name at its fill and at every cancellation rather than paid out of the Diamond's balance. The refusal of other calls during a fill sits in the Diamond's own entry point, which is why it needs a new Diamond. The intent facet and the facet that receives the limit-order protocol's callbacks must be refreshed together on any test or rehearsal Diamond. Nothing is added to storage; a new read reports how much of an auction rests in the Diamond — always nothing on a fresh deploy — for the custody census.

**Limits, stated.** Mirror chains see the borrower's reduced tier only at the borrower's next pushing action, as for the fallback moves. A commit can now be accepted that no fill can complete — a mandatory vault upgrade imposed during the auction (anyone may run the upgrade, which unblocks it), or a collateral or principal token that does not move exact amounts — because the commit no longer moves anything; nothing is lost, the auction stays cancellable, and the intent token allowlists are meant to admit only exact-transfer tokens. The pull is shown on the loan's activity timeline under the fill; the fill event, which the indexer already handles, still closes the loan. A test or rehearsal Diamond cannot be brought across this change by an in-place refresh at all: the refusal of other calls lives in the Diamond contract itself, so both refresh scripts now refuse a Diamond from before it. Refs #1566, #2141, #658.
