## App and agent — Push alerts are offered only when they can be sent (PR #2665)

**The app no longer offers Push alerts a deployment cannot deliver (#2251).** Until now the Alerts card offered the Push opt-in whenever the app was built with a channel address, whatever the agent could actually do. A deployment with no Push signing key, or with a malformed one, still showed the opt-in, accepted it and saved it, and no alert ever arrived. The agent now answers one question for the app: can Push alerts be sent from here, and through which channel. The card offers the opt-in and the subscribe link only when the answer is yes, and the link opens the channel the agent names, so a build-time address can no longer point at the wrong channel. When the answer is no, or the agent cannot be reached, the card says so and offers nothing. The agent also refuses a Push opt-in at save time when it cannot send; the rest of the save is kept, the card states that Push was not switched on, and it re-reads the status. A wallet that already opted in keeps its choice, and delivery resumes once the rail is working again.

**The signing key may now post as a delegate of the channel (#1456).** The Push sender lives in one shared module that both Workers can use, rather than a copy inside the agent. An operator may set the channel's address beside its key; the key then signs as a delegate of that channel, so the channel owner's key need not sit on the Worker and a compromised signer can be removed by the owner without moving the channel. With no channel address set, the key signs as the channel itself, as before.

What the status covers is stated in the answer itself: it is the agent's rail only. The keeper still sends its health alerts with its own copy of the sender until it moves onto the shared module; that move belongs to the keeper work.

Closes #2251. Closes #1456. Part of #2248.
