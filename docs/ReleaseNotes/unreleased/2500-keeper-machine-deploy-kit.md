## Thread — The keeper's always-on machine gets an install kit and deploys itself (PR #<n>)

The keeper can already run as one long-running process off Cloudflare. This change adds what it takes to put it on a real machine and keep it current there. One install script, run once on an Ubuntu machine, installs Node 22 from nodejs.org (checked against its published checksum), clones the repository, and sets up two systemd services. The keeper service runs the keeper as a locked-down, short-lived user that receives its settings file as a private credential. An update timer checks the main branch every five minutes and moves the keeper onto each new build. The install never starts the keeper: that is a separate step in the runbook, taken once its settings are in place.

A merge to main is now the keeper's deploy on the machine, as it is for the Workers. The updater builds the keeper as one self-contained file and runs it once to prove it loads. It compares that file with the one already running, so a merge that does not change the keeper does not restart it. Each build is made from an export of exactly the commit being deployed, inside a throwaway sandbox account that exists only for that build. The sandbox can neither read the keeper's settings or signing key nor write the releases the keeper runs, so code being built cannot change what is already deployed. The updater itself installs the finished file under a folder named for that commit, then switches the keeper to it, and the keeper restarts after its current tick finishes. Rolling back is pointing the keeper at an earlier release and pausing the timer. If a build fails, the running keeper is left as it was and the next check retries. Nothing stops the keeper by force on a timer, because a forced stop could cut a transaction off between sending and recording. The keeper also starts with an empty environment, so its settings file is the only place a setting can come from.

The settings file now has a committed template. It ships disarmed with every secret blank, and a test keeps it in step with the settings the keeper reads, so a setting cannot be left out by accident. An empty line in that file now means "unset", as an unbound setting does on the Worker. Before this, an empty numeric setting could have been read as zero instead of falling back to its default. The new runbook covers starting the keeper disarmed, what a good tick looks like, and arming.
