## Thread — the live testnet drives read the chain through the app's answer-shape rule (#2841)

Since #2812 the app, its protocol console and the indexer decode a configuration answer only when its length matches the build's ABI, because the usual decoder reads a static answer by position and silently ignores anything extra. The live testnet drives still used that decoder for their own chain reads, so against a Diamond whose facet was not the build under review a drive could read a neighbouring field (for example, as the offer duration cap) and use it in a pass-or-fail check. That was contained only by the rule that the drives run after a deploy, against a chain refreshed to the build.

Every drive now makes its chain client through one driver function that applies the same shared rule to contract reads and batched reads. An answer to a fixed-shape getter of any other length is not decoded, and the run ends BLOCKED with the reason, naming the getter, the two lengths, the contract and the block. The driver applies that outcome when the process exits, so it holds even where a drive's own error handling would have swallowed the failed read or reached a pass or fail after it; a malformed request from the page is still reported as a failure first, as before, and a drive that already ends undetermined (it wrote to the chain and could not settle its claims) keeps that outcome with the reason added. Reads whose length is not fixed, simulations of writes, and the test wallet's forwarding of the page's own requests are unchanged. Wherever the shape matches, the drives get exactly the values and errors they got before.

This changes test tooling only; no user-facing page or contract changes. Closes #2841.
