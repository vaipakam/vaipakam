# Security alerts read from the vault itself (#3346)

Since the protected record moved into each account's vault, a lock and a proposed replacement of the primary wallet are announced by the vault, not by the platform's main contract, and the indexer does not record the vault's events. The owner alert step was still looking for them in the indexer's record, so those two alerts had stopped firing. The keeper now reads the vaults' security events from the chain itself, and alerts the account's manager on a lock, a proposed replacement, and every request that loosens protection: an unlock, a shorter delay, switching protected mode off, adding or removing a signer, adding a payout destination, setting or clearing the recovery address, and switching the recovery claim on or shortening its wait. Two Ready balance changes are alerted too, from the main contract's own events: a move from Protected to Ready, and a longer or switched-off idle period.

This is the lasting design, not a stopgap: safety alerts do not depend on the indexer. Because anyone can deploy a contract that emits events of the same shape, the keeper keeps its own list of real vaults, built from the main contract's vault-creation events, and ignores any event from another address without spending a chain read on it. An event from a real vault must name that vault's owner, and is confirmed against the main contract's record before anyone is told.

Each alert says who asked, when the change takes effect, and to lock the vault in the app if it was not them. They ship disarmed under the existing `PROTECTED_ALERTS_ENABLED` flag.
