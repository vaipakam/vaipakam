## Thread — A real illiquid-collateral loan refinanced through the live app; indexer ingest restored (PR #2434)

Loan 22 on Base Sepolia was refinanced end to end through app.vaipakam.com on 5 October, using the dev test wallets. That loan is backed by illiquid collateral that both parties consented to, and it is the loan whose refinance used to fail (#2380). The borrower posted the refinance request from the loan's page (request #45, 12% for 30 days). A different lender funded it through the app's own review-and-sign steps. All five transactions succeeded, and each wallet's transaction count rose by exactly the transactions the drive saw.

What the committed drive verifies. Its claims were narrowed after review (#2431) to what the accept transaction's own record and chain reads taken at the accept's block prove directly. There are three. First, the old loan is closed as repaid. Second, the accept opened exactly one replacement loan, which is active, belongs to the same borrower and is lent by the lender who accepted. Third, the collateral moved with the loan: the old loan's hold on it is released, the new loan holds the same collateral in the same amount, still locked in the borrower's own vault, and the accept moved none of it out of the borrower's vault. The drive also confirms that every signature and transaction was one it expected, and that nothing reached the chain that it had not allowed. On loan 22 all three hold: loan 22 is repaid, loan 23 is active for the same borrower and lender, and loan 23 holds the same 100 units of collateral that loan 22 released.

What this drive does not verify, and says so in its report. It does not check the exact amounts the refinance settled: what the old lender can claim, how each wallet and vault changed, the individual token transfers, or the fee rates recorded on the new loan. Those are covered by the contract test suites, including a test that replays this refinance against a copy of the live chain. It also does not re-check the new loan's other terms beyond the three claims. The requests the wallets signed are still compared field by field before signing, but what the protocol stored from them is not re-asserted. The figures on the review screens are checked before consent, as a reason to stop, not as a result. Out of scope as well: a refinance inside the grace window, a loan with liquid collateral, the old lender claiming the payout, how the indexer and the app's lists show the request and the new loan afterwards, reward accounting, and any payoff approval left standing. The app approves the payoff for the request's last fillable moment, so an earlier accept leaves the difference approved; this run left about 0.0000764 WETH. The drive reads state at the end of the accept's block, so a later transaction in that same block could in principle change what it reads. That is stated in the report too.

How the drive reports a problem. Before it writes anything, a failed check is a failure and a missing precondition stops the run without writing. Once it has written something, any stop is reported as undetermined. It lists what the run may have left standing and the state of any replacement loan, and it never claims success. It reports a failure after a write only when the chain contradicts one of the three claims: the old loan still active after the accept went through, no single replacement loan, or the collateral not carried over. It also fails when more transactions reached the chain than it allowed. If the page fails after the accept went through, the drive still checks the three claims from the chain.

The drive is committed as a reusable live check, and a rerun against loan 22 now stops before sending anything because the loan is closed.

The drive turned up two things, each filed. First, the lender's review never says the request is a refinance: it does not mention that accepting also pays off and closes the borrower's existing loan, and it describes the carried-over collateral as newly locked (#2421). Second, the production indexer had stopped advancing at 05:35 UTC. The merge that added the offer collateral-range columns was published automatically without its database migration being applied, and the safety check added the same day correctly held all indexing until the schema caught up. The two pending migrations, both of which only add columns, were applied by hand at 09:02 UTC, and indexing resumed on its next scan with no redeploy; it was advancing again by 09:06. Until then, today's new offers and loans were missing from the app's lists. Making the automatic deploy apply migrations first, and alerting when indexing pauses, is tracked in #2420.
