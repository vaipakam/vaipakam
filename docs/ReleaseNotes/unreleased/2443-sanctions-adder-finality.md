## Thread — The sanctions adder confirms finality from the list itself (PR #2594)

The sanctions adder's first run on the keeper machine updated both test lists, yet reported the Base Sepolia update as "reorganized out" and marked the run failed. The update was in fact final. The finality check had compared the transaction's block against the one first seen, in a single read, and treated any failure of that read as a lost transaction.

The adder now confirms an update by what the list itself shows at the finalized block, read the same way every update is computed: one snapshot, with every read pinned to that block. Every transaction the run sent must be shown by the same reading; nothing seen in one reading is carried into the next, since two readings can come from different servers. The list keeps the version at which each address was listed, and the publication and outstanding counts of its latest update only. So a transaction counts as final once every address it added is recorded as listed at the version it was built for, and, while it is still the latest update, the list also records its publication and the outstanding counts it declared. That record survives later updates, so a newer publication applied soon after does not make a final update look lost. The outstanding additions and delistings the report gives are read from that same reading. No transaction receipt decides it any more, because a receipt and the finalized block can come from different servers behind one RPC address, and a reorg can move a transaction to another block. A failed read is read again every 15 seconds for up to 40 minutes instead of becoming a verdict. Another update at a transaction's version stops the chain at once, since that transaction can never apply. When later updates have moved the list on and it no longer records a transaction (an address it added was delisted since, or it added none), the report says its outcome is unknown rather than guessing. When the wait runs out, the report says for each transaction what is known: not yet shown by the finalized list (it may still land), or unknown because the list could not be read.

The same run's ops alert was refused by Telegram with HTTP 400, and the report carried only the status code. Both sanctions services now record Telegram's own reason, such as "chat not found", so a refused alert names its cause. Refs #2443.
