## Thread — The sanctions adder confirms finality from the list itself (PR #2594)

The sanctions adder's first run on the keeper machine updated both test lists, yet reported the Base Sepolia update as "reorganized out" and marked the run failed. The update was in fact final. The finality check had compared the transaction's block against the one first seen, in a single read, and treated any failure of that read as a lost transaction.

The adder now confirms an update by what the list itself holds at the finalized block, read the same way every update is computed: one snapshot, with every read pinned to that block. A chain is reported as applied only once one such reading holds exactly the update the run planned: at the update's last version, the planned addresses with nothing extra and nothing removed, this publication, and the outstanding counts the update declared. Nothing seen in one reading is carried into the next, since two readings can come from different servers. Finality is now stated as a fact about the list rather than about any transaction, because no reading of the list can say which transaction produced it; the report names the transactions sent and the reading that holds the update. No transaction receipt decides it any more, because a receipt and the finalized block can come from different servers behind one RPC address, and a reorg can move a transaction to another block. A failed read is read again every 15 seconds for up to 40 minutes instead of becoming a verdict. A list that reaches the update's last version holding anything else stops the chain at once, since the planned update can never apply. A list that has already moved past the update before a reading showed it is reported as an unknown outcome rather than guessed at. When the wait runs out, the report says whether the update may still land or could not be checked at all.

Every report now also states what the list declares outstanding, refused and stopped runs included, using the last finalized reading and naming which publication it belongs to. The delistings this run computed are named only when that reading records this publication, so a newer publication applied in the meantime is never paired with an older file's addresses.

The same run's ops alert was refused by Telegram with HTTP 400, and the report carried only the status code. Both sanctions services now record Telegram's own reason, such as "chat not found", so a refused alert names its cause. Refs #2443.
