## Thread — The sanctions adder confirms finality from the list itself (PR #2594)

The sanctions adder's first run on the keeper machine updated both test lists, yet reported the Base Sepolia update as "reorganized out" and marked the run failed. The update was in fact final. The finality check had compared the transaction's block against the one first seen, in a single read, and treated any failure of that read as a lost transaction.

The adder now confirms an update by what the list itself shows at the finalized block, read the same way every update is computed: one snapshot, with every read pinned to that block. A call is final once that list is past the call's version, records the publication and lists every address the call added. No transaction receipt decides it any more, because a receipt and the finalized block can come from different servers behind one RPC address, and a reorg can move a transaction to another block. A failed read is read again every 15 seconds for up to 40 minutes instead of becoming a verdict. A list that has moved past a call's version without showing it stops the chain at once, since that call can never apply. When the wait runs out, the report says for each transaction what is known: not yet shown by the finalized list (it may still land), or unknown because the list could not be read.

The same run's ops alert was refused by Telegram with HTTP 400, and the report carried only the status code. Both sanctions services now record Telegram's own reason, such as "chat not found", so a refused alert names its cause. Refs #2443.
