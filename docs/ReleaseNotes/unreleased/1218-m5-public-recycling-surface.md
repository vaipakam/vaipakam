## Thread — the public recycling account is back in the app, it answers "is the pool backed?" by the relation the chain's custody state selects, and loop closure is shown for the first time (#1218 / #1349 M5)

**Problem.** The public recycling account — the per-day record of where each day's reward pool came from, how much of the scheduled fresh amount was actually drawn, how much value the programme absorbed back, and the retained reserve beside the balance that backs it — was rendered by the old dashboard app. When that app was retired, the indexer kept serving every figure, but nothing in the connected app or the marketing site displayed them, so the transparency the programme promises was only reachable by calling the indexer directly. The loop-closure figures (how much of what reward claims distributed stayed inside the platform) had never had a display home at all. Separately, the old dashboard decided "is the pool backed?" itself by comparing the platform's balance with the recycle bucket alone, which was wrong in both custody states: before reward custody is activated it ignored the two recovery reservations held inside the same balance, so a balance that had spent reserved value could still read as backed; after activation the bucket and the recovery position are held by the custody holder, so the same comparison would call a healthy chain short. The stored reading also carried no record of which state the chain was in.

**What changed — the indexer.** The scheduled capture now reads the versioned backing view, which adds the activation state and the holder's balance and attributed total to the eight figures already stored, all at the same settled block. The read surface publishes those four figures and, beside them, a stated verdict: whether the pool is backed, which relation decided it, and how far each side falls short when it does. Before activation the platform's balance must cover the bucket plus both reservations; after it, the holder must cover everything attributed to it and the platform must still cover its one remaining reservation. The comparison is exact, with no tolerance, so a published answer always agrees with the published figures. One shared function decides the verdict, and it lives in the contracts package so no consumer has a reason to work the relation out again. Where the reading cannot establish the answer, the verdict says so and gives the reason instead of guessing: the custody state is unknown (a reading taken before this change, or a platform contract that does not include the versioned view — non-activation is never assumed, because the activation flag lives on the same facet), the holder's balance could not be read, or a figure the relation subtracts is missing. Older readings keep being served with all their figures; only the verdict is withheld for them.

**The new database columns, and a deploy that skips them.** The custody columns arrive in indexer migration 0056 (renumbered from the number first chosen, which main had since taken; a duplicate number fails the indexer's migration-prefix check and would let a fresh environment replay the two files in the wrong order). The Worker deploys before migrations are applied, so while the columns are missing the capture still stores the eight figures and the read still serves them, with the custody state unknown. Those fallbacks are no longer silent: each logs a warning naming the missing migration, and the backing block publishes the name of the migration it is waiting for, so a migration that failed or was skipped cannot pass for the ordinary "older reading" state and leave every chain's verdict undetermined with nothing saying why. The ops mesh watcher still evaluates the same relation for its alarms with a dust tolerance appropriate to paging; moving it onto the shared function is tracked in #2433.

**What changed — the page.** The connected app's public analytics page, which loads without a wallet, now carries the recycling account again. Days are identified by the programme's own day index, never converted to calendar dates. A day that has not been finalized is shown as having no pool rather than a pool of zero; a day finalized before the governor was armed is shown as an estimate with no net emission; a positive amount too small for the page's precision is labelled as below that precision rather than shown as zero; the self-funded share of a day rounds down, so a day that still drew any fresh amount never reads as fully self-funded; and every total on the page is the one the indexer published — the page adds nothing up itself, and a total the indexer declines to state is shown as declined with its reason. The retained reserve is shown with the moment its reading describes and with every amount subtracted to reach it, or withheld as a whole with the reason no current reading is available. The backing answer is the indexer's own: the page names which comparison decided it, states any shortfall as the indexer published it, and shows "not determinable" with its reason when the reading does not establish the answer. The page checks the published answer against the figures published beside it without comparing any amounts: an answer that a reading with a missing figure could not have produced — for example one leg's shortfall offered as the whole answer on the two-leg relation — is withheld rather than shown.

**Loop closure.** The same page shows the loop-closure series for the first time: per UTC calendar day (the day the tokens left the platform, which is deliberately not aligned with the programme's days, and labelled as such), what claims distributed, what stayed in user vaults, what the platform absorbed, and the share retained, plus the lifetime figures. A complete day on which nothing was distributed shows the share as not applicable, never as zero. The indexer used to pad every day of the window with zeros, so the day in progress and any day it had not yet reached read as days on which nothing was paid out. It now records how far its record of claims reaches (stamped whenever its ingest catches up with the chain, and never moved backwards) and publishes that moment with the series, marking each day as complete, still being recorded, or not yet reached. The page shows the moment; a day still being recorded shows its amounts so far and no share, because a share of an unfinished day could overstate the final one; and a day the record has not reached shows as not yet recorded in every cell.

**Wording.** Every new string ships in every language the app supports. Two sentences were reworded across all of them for the release-gate copy rules: the withheld-reserve notice no longer says there is no reading the platform "can stand behind" (rendered in several languages as the platform guaranteeing the figures; it now says no current reading is available), and the caveat on the drawn figure no longer describes a later disbursement as "operator-sized", which framed an amount as someone's discretion. A new test applies the copy rules to every shipped translation of both sections, per language, so a translation can no longer reintroduce guarantee, discretion, return or price vocabulary unnoticed.

**Verification and follow-ups.** The fork-tier suite gains a spec that drives the page against fixed indexer responses: armed and unarmed days, a below-precision amount, a self-funded share that must round down, the pre-activation platform-balance answer both backed and short (the short case stated with the indexer's shortfall), the holder-relation answer, a short holder with the indexer's shortfall, an older reading (its recovery reservations shown as predating the reading, and no comparison chosen), a not-determinable answer and a withheld reading, and loop closure's not-applicable, still-being-recorded and not-yet-recorded days with the series' recorded-up-to moment. The scheduled capture, the time watermark and the live indexer history can only be observed on the deployed services, so that half is reviewed live after the end-of-programme deploy.

**Spec:** TokenomicsTechSpec's recycling transparency section states that the backing comparison depends on where reward custody is held and that a reading which cannot establish it answers not determinable with its reason; its loop-closure section now states that a day is final only once it has ended and every claim in it is recorded, that the recorded-up-to moment is published, and that an unrecorded day is never shown as zero.
