## Indexer — internally matched loans now show as settled once claimed (#2464)

When both sides of an internally matched loan have claimed, the protocol settles it. The indexer kept showing these loans as internally matched anyway, so the loan page, Positions and the desk read as if claims were still pending. The handler for the protocol's settlement event only accepted a hand-written list of earlier states (repaid, defaulted, liquidated) and left internally matched loans out. Meanwhile the handler for general status changes deliberately leaves this step to the settlement event, so nothing ever corrected the row. On Base Sepolia, loans 24–27 were stuck this way.

The indexer now treats the protocol's settlement event as authoritative: it settles a loan whatever state the loan was in. It no longer keeps a second copy of the contract's rules about where settlement can come from. Loans already stuck this way are settled by a check that runs on every indexer pass, not by a one-time migration. A one-time migration would also miss a settlement that the previous indexer version logs during a deploy without updating the loan. The check only finishes the step that was missed: a loan already shown as repaid, defaulted, liquidated or internally matched, whose settlement the indexer's own event log holds. Before changing anything it confirms with the protocol that the loan really is settled, and it takes the settlement's block only from a logged event whose transaction the chain still confirms in that block, so an event from a block the chain later discarded can supply neither the status nor the date. If no logged event can be confirmed, for example because the node no longer keeps old receipts, the loan is still settled, since the protocol confirmed it, with its block and time recorded as unknown. A later confirmed event fills them in. It only acts on a block the chain has called settled. Settlements recorded by the previous indexer version carry the time the indexer noticed them, not when they happened. Those times are now marked unknown, and the same check fills them in from the chain over the following passes. It dates the settlement by reading the event's block from the chain again, because the time stored in the log can be the indexer's own clock when the original read failed; if that read fails, the time is recorded as unknown rather than guessed. The check works through loans in rotation, so loans it cannot confirm cannot hold up the others. It announces each settlement to connected browsers straight away.

A loan still shown as active but with a settlement in the log has missed its whole closing step. That stays the job of the indexer's existing correction pass, which re-reads the full loan.

When the time of a settlement cannot be read during a scan, the loan is settled with its time recorded as unknown, and a later replay of the same block fills it in. The "we found this by checking" notice from the indexer's correction pass is now tied to an explicit marker that only the correction pass sets (a new additive database column), rather than to what the loan's record happens to look like, so it can no longer be attached to a settlement an event or the settle check wrote. A settlement event for a loan the indexer still shows as active is left to the correction pass, which re-reads the whole loan and clears its listings, rather than changing only its status.

Closes #2464.
