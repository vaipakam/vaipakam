## Thread — a confirmed-flagged owner's undelivered interaction reward is forfeited, not held (#1566)

**Problem.** A wallet flagged by the sanctions oracle could not claim its interaction reward, and its entries' removal clock stopped while it was flagged. Nothing else ever moved those entries, so they stood for as long as the flag did. That froze the reward indefinitely, and it also held back the release of every old-wire delivery that listed one of those days, which the delivered-bound design recorded as an open owner question. Separately, the staged claim path that shipped in the staging change (#2308) went the other way: it forfeited a claimant's undelivered share on a single, fail-open oracle read. The owner's rule (2026-10-02) settles both cases. Reward not yet delivered to a flagged wallet is forfeited. Value already in the wallet's vault stays frozen. Loan proceeds are unchanged.

**What changed.** One classifier now decides, for any wallet, whether undelivered reward is delivered, held or forfeited. A flag is *confirmed* only when all of these hold: the oracle reports the wallet flagged now; the platform's committed flag has not been cleared by a clean read since; the classifier's own evidence was recorded under the same oracle; and the evidence forms a chain of flagged observations spanning a three-day window, with no gap longer than one day between observations. Both bounds are fixed. A first flag, a gap over one day, a pause or an unset oracle lasting longer than that, or a change of oracle all start the window again. An unset or unreachable oracle never forfeits anything. A wallet that declared a flagged stuck-token recovery source is treated the same way, as it already was everywhere else. Anyone may record an observation, and every observation is an authoritative oracle read, so no caller can forge or break another wallet's chain.

A new permissionless owner sweep observes the wallet on every call. Once the flag is confirmed, it marks each of the owner's claimable, undelivered reward entries forfeited, one event per entry naming the owner, the loan, the side and the flag time. It then settles those entries through the existing forfeit route into the recycle bucket as forfeited reward. That pricing is untrimmed by the loan-side reward cap, as every forfeit already is. Each settled chunk announces its amounts per entry. The forfeit is permanent: a later delisting restores nothing. The sweep is bounded per call (at most 32 entries and 30 settlement chunks), always advances its position, and reports how many entries still need another pass. Some entries are not marked. An entry whose loan is still open or awaiting its fallback resolution is marked once the loan resolves. An entry whose expiry has already begun finishes as an expiry. An entry whose day is held by a resolving staging record, by an expiry's staging record or by a resolving staging domain is left to that record. The existing per-loan forfeit sweep now announces the same per-entry settlement event, and it refuses to settle an entry that is not actually marked forfeited.

**Claims, clocks and keepers.** The claim now refuses any *barred* owner: one flagged now, and also one carrying a committed flag (the #1123 marker) while the oracle is unreachable. Before, the ordinary fail-open screen would have let that owner through during an outage. The removal clock's sanctions pause moved to the sweep's entry point and uses the same barred test, so the clock and the claim gate always agree. A forfeited entry shows no removal countdown. A keeper carrying a committed flag (the #1123 marker) is skipped for its keeper reward during an outage, where before it was paid. Two new read views show a wallet's confirmation status and its forfeitable entries. The status view gives the decision, when the flag was first and last observed, when the window completes, the deadline for the next observation and the evidence oracle. The forfeitable-entries view uses exactly the eligibility rule the marking uses, so the two cannot disagree.

**Behaviour change to the staging change (#2308).** A staged claim's last page no longer forfeits on one read. If it carries a user share, it consults the classifier. With a confirmed flag it forfeits exactly as before. With an unconfirmed flag, or with a committed flag (the #1123 marker) while the oracle is unreachable, the page records the oracle observation, pays and retires nothing, and is retried later. It forfeits once the window completes, and it pays the claimant if the wallet is delisted first. A last page with no user share never waits, and expiry, forfeit and legacy records are never screened. While a page waits, its record still counts as encumbering staging, and that blocks reward-custody activation and reward-role changes. The wait is bounded by the three-day window when someone observes the wallet at least daily, and by the outage otherwise.

**Accounting fix.** Two headroom subtractions in the existing expiry sweeps could underflow when a chunk reported more than the remaining headroom. They are now floored at zero, like the new sweep's.

**Refresh together.** The staging settlement facet, the horizon sweep facet, the forfeit walk facet and the expiry sweep's walk facet (RewardStagingSettleFacet, RewardHorizonSweepFacet, RewardForfeitWalkFacet, RewardSweepWalkFacet) must be refreshed together on every chain. The staging settlement facet's last page calls the evidence recorder hosted on the horizon sweep facet, so a settlement facet refreshed without it reverts every staged claim's last page that carries a user share. The owner sweep reaches the forfeit walk facet's new chunk entry. The expiry sweep's walk host (RewardSweepWalkFacet) no longer screens sanctions itself, because the screen now runs in the horizon sweep facet in front of the walk, so the two must be refreshed together, or the horizon sweep facet first; a walk facet refreshed alone would run the removal clock for a barred owner. The full in-place refresh covers all four. The staging records' read views also move, with the same selectors, from the epoch view facet to the staging domain facet (RewardEpochViewFacet to RewardStagingDomainFacet): the view facet sat a few hundred bytes under the contract size limit, and this release's library growth tipped it over although none of its own code changed, so the reads moved to the staging facet that already hosts the domain reads. Those two facets must be refreshed together as well; an epoch view facet refreshed alone drops the staging reads until the domain facet carries them. The new selectors are additions, so a curated refresh must add them rather than replace them. Storage gains one appended field, the per-wallet evidence record. This branch carries no storage-slot pin file or layout era table; when the stack meets the branch that does, both must be regenerated to include the new field.

**Limits, stated.** Without a caller observing at least daily, a flagged owner's reward is only withheld, never forfeited; the keeper's sanctions-hold observer (#2450, its own entry) is that caller. Any app copy is the owner's call. The oracle setting now carries a delayed reward-forfeit power: an oracle that flags a wallet forfeits its undelivered reward after three days. Timelock and pause are the mitigation, and unsetting the oracle stops every forfeit and delivers instead. These cases stay frozen rather than forfeited: a flagged lender's entries on a loan awaiting its fallback resolution, the rewards of a principal behind an aggregator adapter, and vault reward VPFI, whose withdrawal stays fail-open during an outage as before. The borrower's fee rebate is loan value and is unchanged; its wallet fallback without a sanctions screen is a separate gap for a follow-up. A delisting shorter than one day that nobody observes can sit inside a confirmed chain. That is the same sampling limit as the expiry heartbeat's. Refs #1566.
