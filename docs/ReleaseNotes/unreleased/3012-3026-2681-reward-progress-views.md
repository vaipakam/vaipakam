## Contracts — reward close-out progress and the grace window in force (PR #TBD)

The two permissionless reward close-out calls now say whether they made progress, not only how much VPFI they moved. The forfeited-reward sweep of a loan returns the amount it swept and a progress flag, and the retirement of zero-priced remainders returns its retired count, the commitments it released and a progress flag. A call can move nothing and still advance the settlement (it prepares a legacy slice, stamps or advances an entry's settlement cursor, retires a commitment, or advances its side's cumulative pricing cursor), so the amount alone could not tell a funding wait from real work. A keeper that sent only on value could stall a backlog whose cursor was more than 730 days behind; one that sent every round paid for no-ops. Closes #3012 and #3026 (contracts half).

The flag is measured by the protocol itself, before and after the call, over one set of fields: whether each entry is settled or forfeited, its settlement cursor, its side's pricing cursor, and its legacy-slice domain's phase and cursors. A legacy slice that is staging counts as progress by itself, because a step can work inside one day record without moving those cursors. The same fields are published through a new lens read, `getRewardEntrySettlementProgress`, so anyone can see where a forfeited entry's settlement stands. No value moves differently: both calls settle exactly as before.

The reward day-close grace getter now returns the window in force. While governance never set one, `getRewardGraceSeconds` reports the default four hours instead of zero, the same figure the finalization rule and the reporter configuration snapshot already used. The default is now applied in one place. Closes #2681.

These are contract changes, and they reach a chain only through the next fresh deploy. Until then, the live testnet Diamonds keep the old return shapes. So the keeper's reward heartbeat now reads the two close-out results through a narrower shape that decodes both the old and the new result. Its behaviour is unchanged. Reading the new progress flag (simulate, and send only on progress) is the keeper's own follow-up, and it replaces that bridge after the fresh deploy. The protocol console's "not set, so the default applies" wording for the grace row can go once every chain runs this code.

> Caveat: the progress flag can over-state progress in one narrow case, a staging legacy slice whose next day the pricing curve has not reached. That costs a caller one transaction. It never under-states progress, so no entry stalls.
