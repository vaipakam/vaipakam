# Live testnet reviews (post-deploy DoD)

Per the standing directive in CLAUDE.md, every user-facing merge to a
deployed surface gets a LIVE review on the deployed testnet site
(alpha02.vaipakam.com) **after the production deploy** — driving the
real feature end-to-end with the dev test wallets and confirming the
observable behaviour, not just preview builds or CI.

These are the reusable Playwright drivers for those reviews. They are
NOT part of any CI job (the fork-tier suite under `../tests/` is the
automatic regression); they run manually, post-deploy, against the
live site. The results belong in the PR thread of the change under
review — see e.g. #1059, where this exact drive produced the
before/after evidence for the classifier fix.

## Running

```bash
# from apps/alpha02/e2e/live/
TESTNET_WALLETS_FILE=~/secrets/vaipakam-dev-wallets.json \
  node live-dryrun-review.mjs

# target a branch preview instead of production:
SITE_URL=https://<branch-preview>.workers.dev node live-dryrun-review.mjs
```

- `TESTNET_WALLETS_FILE` — JSON of dev TEST wallets (throwaway keys
  holding testnet dust). **Never commit this file.** Shape:
  `{ "lender": { "address": "0x…", "privateKey": "0x…" }, … }` or an
  array of `{ role, address, privateKey }`.
- `SITE_URL` — defaults to `https://alpha02.vaipakam.com`.
- `LIVE_PROXY_SETUP` — optional path to an egress-proxy shim module,
  for sandboxes whose gateway resets Chromium TLS (the driver then
  routes page traffic through undici in-process). Honoured by
  `driver.mjs` (so every signing drive), `live-desk-i18n-capture.mjs`
  and `live-position-observe.mjs` — i.e. by every driver that pumps
  page traffic through this process. A driver that documents the knob
  but never imports it fails every routed request in such a sandbox
  with no hint that the shim was ignored, so keep the import next to
  the fetch capture when adding a new one.
- `FAUCET_JSON` — optional deployments artifact for the faucet mock
  token addresses (defaults to the live Base Sepolia set).

The post-wait re-read is **not** gated on the card being gone: the card deliberately survives FallbackPending, maturity and a position lock while both jumps are removed for exactly those states, so a jumpable pre-state that stops being sellable during the wait is exit 2 whether or not the card is still up — gating on presence skipped precisely the states the card is designed to survive. The probe therefore samples the chain sparsely DURING its wait — roughly every eighth poll tick, stopping once it has seen something — and an excursion it catches is exit 2. Sparse means incomplete: a transition that opens and closes between two samples is still invisible, which is a smaller gap than the one it replaces and not a closed one. #1855's readiness attribute removes the guess rather than narrowing it. A card that WAS scraped and is now absent is exit 2 on that DOM evidence alone, because a transition that reverses inside the window (sold, the 60s ownership poll unmounts, sold back) leaves two identical chain samples and is invisible to any before/after. And the scrape can be too EARLY as well as too late: where the probe observes a card the initial scrape missed, its later reading REPLACES the earlier absence — a card cannot un-render into having been there — without which a healthy late-rendering page was reported as a missing chooser on the very visit that had just audited its anchors. That replacement is banked ONCE, as early as the probe can see the card, and merged at the probe's single exit — an earlier version spread it into only the two returns that carry an anchor audit, so a card that mounted late and legitimately had no jumpable row (a past-maturity position, which is most of the live chain) kept the scrape's absence and was filed as a missing chooser by the probe that had just read its text. The comparison is a BEFORE/AFTER snapshot taken before the switch is even observed — a post-hoc read would call a pre-existing state a race, which excuses the very no-op-switch regression the FAIL exists to catch. Only an unmoved loan with no jump is the no-op-switch FAIL. A probe that cannot RUN (switch present but unclickable, or a page evaluate that throws) is **exit 2**, not a FAIL and not a pass: nothing was learned about the app, but the advertised assertion did not execute. No-switch reasons are reported separately (already in Advanced, no jumpable row, prerequisite read failed, probe error). **Absence of a switch is conclusive only at the 45s deadline — and only when the rows have stopped saying they are still reading.** A deadline reached while the sale rows still show the checking sentence is a failure to observe (exit 2), not an observation of no jumpable row: the clock settled, the page did not. There is no positive readiness signal available from outside the card — it carries no test hook (#1855) and the only DOM evidence a row became jumpable IS the jump button — and neither an enumeration of loading sentences nor DOM-text stability is sound: at least four transient states remove the switch and jumps together, and pending copy is STATIC, so "unchanged text" means the loading message has not changed, never that the read finished. ## Watch-only drives vs. signing drives

Three drivers need no `TESTNET_WALLETS_FILE` at all:

- `live-desk-i18n-capture.mjs` — read-only locale capture of PUBLIC
  surfaces, never connected to a wallet.
- `live-position-observe.mjs` — observes a real address's real chain
  state through an injected watch-only provider holding no key, so it
  reaches CONNECTED surfaces (the position pages) that a public-only
  capture cannot.
- `live-recover-locales.mjs` — launches with `keyless: true`, so no
  wallet is injected at all and no key is read. It reads only the
  public `/recover` chrome, and pairs `keyless` with `readOnly` —
  separate guards: the first removes the wallet, the second stops the
  route shim forwarding a page-initiated write.

Every other driver signs, and needs the file. That is unavoidable for
the write half of a review — but it made the READ half unrunnable too
whenever the funded-wallet secret wasn't to hand, and the read half is
where a render crash, a missing card, or a mis-decoded chain value shows
up. `live-position-observe.mjs` is the pattern for closing that gap on a
wallet-gated surface: the read-only guarantee is structural (no key
exists in the process) rather than a flag that could be passed wrong.

Prefer it when what you need to confirm is *what the deployed build
renders for real on-chain state*. Reach for a signing driver only when
the behaviour under review genuinely requires a transaction.
